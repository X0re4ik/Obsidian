## Необходимые условия для применения RVO/NRVO

1. Тип объекта, возвращаемого из функции согласно сигнатуре, должен совпадать с типом локального объекта или конструироваться неявно из типа локального объекта. Допустимо отличаться на константность
2. Возвращаться должен именно локальный объект, а не ссылка на него или какая-то его часть
3. В случае NRVO возвращаемый объект не должен быть `volatile`, так как `volatile` исключает любого рода оптимизации

## Сложности оптимизации RVO/NRVO компилятором

1. Есть несколько путей выхода из функции, которые возвращают локальные объекты.
2. Возвращаемый локальный объект ссылается на встроенный `asm`-блок

## Обязательное примнение RVO

Рассмотрим случаи, когда применяется `RVO`:
1) Функция возвращает `prvalue` того же типа, что описан в сигнатуре функции.

Уточнение:
* Операторов `return` может быть несколько, важно, чтобы они все возвращали один и тот же тип с категрирей `prvalue`
* RVO применяется и к неявным преобразования, напрмиер, при отсутвии `explicit` конструктора в классе

**Пример:**
```C++
struct Class {
  Class(int);
};

Class getClass1() { // RVO: ✅ (Возврат только prvalue)
  return Class{1};
}

Class getClass2(int x) { // RVO: ✅ (Возврат только prvalue)
  if (x == 0) {
    return Class{0};
  }
  return Class{-1};
}

Class getClass3(int x) { // RVO: ✅ (Неявно создание объекта)
  return x;
}
```

`RVO` гаранирован, начиная с `C++17`. Рассмотрим пример того, как можно воспринимать `RVO`

**Пример (Сгенерирован DeepSeek)** 
```C++
// псевдокод того, что генерирует компилятор
void getClass3(Class* R, int x) {
  if (x == 0) {
    Class tmp;              // отдельный объект на стеке (если NRVO не сработал)
    tmp.Class::Class(0);
    *R = std::move(tmp);    // или копирование
    return;
  }
  // ветка RVO:
  R->Class::Class(-1);      // конструируем ПРЯМО в слоте возврата
  return;
}
```


## Возможности применения NRVO

NRVO **не обязателен** ни в какой версии `C++`, соотвественно любой класс, который мы возвращаем из функции **обязан** иметь хотя бы один из конструкторов: конструктор копирования, уонструктор перемещения.

Рассмотрим случаи, когда применяется `NRVO`:
1. Возвращение объекта по значению
2. Переменная не является параметром функции
3. Переменная не `volatile`
4. Возвращаемый тип является тем же типом или совместим с типом локального объекта

**Пример:**
```C++
Class getClass1() { // NRVO: ✅
  auto tmp = Class{1};
  return tmp;
}
```


Если `NRVO` не сработало, то компилятор постарается вызвать:
* Конструктор перемещения
* Конструктор копирования

Рассмотрим пример того, как можно воспринимать `NRVO`

**Пример (Сгенерирован DeepSeek)**
```C++
// Псевдокод, не нормальный публичный API:
void getClass1_hidden(Class* out) {
    std::construct_at(out, 1);
}

int main() {
    Class result;              // место под итоговый объект
    getClass1_hidden(&result); // компилятор условно передал &result
}
```


## Тест-кейсы с собеседования

### Задание №1

```C++
struct T {
    T();
    T(const T&);
    T(T&&);
    ~T();
};

T make() {
    return T{};
}

int main() {
    T x = make();
}
```

**Вопросы:**
- Сколько раз будут вызваны конструкторы и деструкторы в C++14 и в C++17 при обычной компиляции без `-fno-elide-constructors`?
- Почему ответ для C++17 отличается или не отличается?
- Является ли здесь оптимизация copy elision обязательной по стандарту?

**Ответы:**
1) Перед нами пример работы `RVO` (`Return Value Optimization`), данная оптимизация гарантирована только с `C++17` версии, но в `C++14` она возможна, но не гарантирована. Отметим, что пример тривиальный и, скорее всего, `RVO` отработает в двух версиях. Для `C++17` последовательность будет следующей: `T()`, `~T()` - то есть сработает `RVO` и объект буд создан "на месте". Для `C++14` (при не сработавшем `RVO`) последовательность будет следующей: `T()`, `T(T&&)`, `~T()`, `T(T&&)`,  `~T()`, `~T()` - то есть создание локального объекта, передача его в `result object`, а после его перемещение в объект `x`
2) Отличаться он будет только по причине того, что в `С++17` **гарантирован** `RVO`. Даную оптимизацию так же именуют **URVO** (`unnamed return value optimization`)
3) Оптимизация обязательна только для `C++17` версии

### Задание №2

```C++
struct Token {
    Token() = default;
    Token(const Token&) = delete;
    Token(Token&&) = delete;
    ~Token() = default;
};

Token create() {
    return Token{};
}

int main() {
    Token token = create();
}
```

**Вопросы:**
1. Компилируется ли программа для `C++17` и `C++14`?
2. Нужен ли компилятору доступный copy- или move-конструктор для `C++17` и `C++14`?
3. Что изменится для `C++17` и `C++14`, если тело `create()` заменить на:
```C++
Token token;
return token;
```

**Ответы:**
1) Для `C++17` - да, для `C++14` - нет
2) Для `C++14` необходим один из конструкторов: копирующий или перемещающий. Так как они оба удалены, то компилятор не сможет передать объект наружу. Все из-за того, что в `C++14` версии не гарнтирован `RVO` (`URVO`) и для `fallback` решения необходим один из конструкторов. В `C++17` `RVO` (`URVO`) строго гарантирован, поэтому подобный код отработает даже при удаленных конструкторах копирования и перемещения.
3) Код не скомпилируется ни на одной из версий. В `C++17` и `C++14` `NRVO` не гарантирован, а `fallback` решения отсутвуют (`move/copy` удалены)

### Задание №3

```C++
struct T {
    T();
    T(const T&);
    T(T&&);
    ~T();
};

T make(bool flag) {
    T a;
    T b;

    if (flag) {
        return a;
    }
    return b;
}

int main() {
    T x = make(true);
}
```

**Вопросы:**
1. Может ли здесь быть применён NRVO для `a` или `b`?
2. Гарантирован ли NRVO в этом коде?
3. Если NRVO не выполняется, какой конструктор будет выбран для `return a;` и почему?
4. Сколько объектов `T` существует одновременно непосредственно перед выполнением `return a;`?

**Ответы:**
1) Нет. Создание двух локальных переменных, причем в зависимости от уловий возвращается определённая переменная. Компилятор не сможет выполнить оптимизацию.
2) Нет
3) При невозможности выполнения `NRVO` компилятор рассматривает объекты как категории `xvalue`, приоритет конструктор перемещения, после констпуктор копирования
4) Два объекта

### Задание №4

```C++
struct T {
    T();
    T(T&&);
    ~T();
};

T make() {
    T t;
    return static_cast<T&&>(t);
}

int main() {
    T x = make();
}
```


**Вопросы:**
1. Может ли здесь быть применён NRVO?
2. Если NRVO не применяется, какой конструктор будет вызван для инициализации return object из `t`?
3. Сколько раз будет вызван деструктор `~T()` в `main()` и `make()` вместе, если NRVO не сработает?

**Ответы:**
1) Нет. Запись `static_cast<T&&>(t)` эквивалентна `std::move(t)`. Оптимизация будет исключена в пользу конструктора перемещения
2) Конструктор перемещения
3) 1 раз в `main` и один раз в `make`

### Задание №5

```C++
struct T {
    T();
    T(T&&);
    ~T();
};

T make() {
    T t;
    return t;
}

int main() {
    T x = make();
    T y = std::move(make());
}
```

**Вопросы:**
1) Может ли компилятор применить NRVO для `return t;`?
2) Если NRVO не применяется, сколько раз будет вызван move-конструктор `T(T&&)` в `main()` (суммарно для `x` и `y`)?
3) Сколько раз будет вызван деструктор `~T()` в этой программе, если NRVO не сработает?

**Ответы:**
1) Да, он может и, скорее всего, применит `NRVO` для объекта `t`
2) Если `NRVO` не применится, то `T(T&&)` будет вызван 2 раза, `make()` -> `return object` -> `x` для `x` и столько же для `y`, потому что `std::move` ничего не переносит, а только лишь изменить категорию значения на `xvalue`
3) 6 раз. Cначала уничтожится локальный объект, потом `return object`, а после и основной в `main`. Посколько у нас всего 2 объекта, то 3x2

### Задание №6

```C++
struct T {
    T();
    T(T&&);
    ~T();
};

T make() {
    T t;
    return t;
}

int main() {
    T&& ref = make();
}
```

**Вопросы:**
1) Может ли здесь быть применён NRVO?
2) Если NRVO не применяется, сколько раз будет вызван move-конструктор `T(T&&)`?
3) Сколько раз будет вызван деструктор `~T()` в этой программе при отсутствии NRVO?

**Ответы:**
1) Да, может. Компилятор оптимизирует конструкцию в следующую последовательность:
```C++
void make(T* t) {
  // ...
  return;
}

int main() {
  T&& t = T{};
  make(&t);
}
```
2) 1 раза: `make` -> `return object` - далее `ref` привязывается к уже существуещему `return object`
3) 2 раза: уничтожение локального объекта в `make`, после `return object`, а `ref` лишь ссылается на объект `return object`


```C++
struct T {
    T();
    T(const T&);
    T(T&&);
    ~T();
};

T make(bool flag) {
    T t;

    if (flag) {
        return t;
    }

    return std::move(t);
}

int main() {
    T x = make(true);
    T y = make(false);
}
```

Вопросы:
1) Может ли быть выполнен NRVO?
2) Если NRVO не выполняется, какой конструктор используется для формирования return object?
3) Влияет ли наличие второй ветки с `std::move(t)` на возможность NRVO в первой ветке?
4) Почему `return std::move(t);` обычно считают плохим стилем для локальной переменной, возвращаемой по значению?

Ответы:
1) Нет, `NRVO` возможен, но не гарантирован для первой ветки `if` и невозможен для второй ветки 
2) В обоих случаях ветвеления категория значения будет `xvalue`, для `xvalue` объектов первый приоритет конструктор перемещения, соотвественно для формирования `return object` применится конструктор перемещения
3) Нет, не влияет, так как `NRVO` важно, чтобы **возвращаемый** объект совпадал с **возвращаемым** типом функции, это условие в первой ветки соблюдается
4) Потому что `std::move` сразу же исключает оптимизацию компилятора. Мы явно просим применить к объекту конструктор перемещения. Компилятор так и так возвращаемый объект будет расценивать, как `xvalue`, явного указания не нужно.
