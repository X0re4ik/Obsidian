
Проблематика: для запуска функции в другом потоке нужно сохранить переданную функцию и аргументы так, чтобы их хранение не зависело от времени жизни параметров конструктора и исходных переменных. Если этого не сделать, то поток рискует работать с уже уничтоженными объектами

Решение: над всеми входными данными в поток произвести поверхностное копирование, чтобы сами объекты внутри потока принадлежали только потоку

В `C++` проблема решается при помощи сочетания идеи `std::invoke` ([std::invoke, std::invoke_r](https://en.cppreference.com/cpp/utility/functional/invoke)) и decay_copy ([decay-copy](https://en.cppreference.com/cpp/standard_library/decay-copy))

**Пример (Примерная реализация работы конструктора потока)**
```C++

template <typename Callback, typename... Args>
void run_like_thread(Callback &&callback, Args &&...args) {
  auto stored = std::make_tuple(std::forward<Callback>(callback),
                                std::forward<Args>(args)...);

  return std::apply(
      [](auto &&fn, auto &&...a) -> decltype(auto) {
        return std::invoke(
            std::forward<decltype(fn)>(fn),
            std::forward<decltype(a)>(a)... // rvalue из хранилища
        );
      },
      std::move(stored));
}
```

## Что такое `decay_copy`

`decay_copy` - это операция по созданию значения типа `std::decay_t<T>` из переданных аргументов. По сути копирование объекта с дополнительными преобразованиями.

Правила следующие:
1) Вся ссылочность и верхнеуровневые `const` и `volatile` пропадают
2) Результат создается через копирование или перемещение
3) Массивы и функции превращаются в указатели

Пример реализации `decay_copy`:
```C++
#include <type_traits>
#include <utility>

template<class T>
std::decay_t<T> decay_copy(T&& value) {
    return std::forward<T>(value);
}
```

## Как передавать в поток аргумент по ссылке

При работе с потоками `decay_copy` уберет все ссылки и `cv-классфикаторы`, поэтому передача аргументов по ссылке является нецелесообразной.

**Пример (При передачи по ссылке присходит копирование аругмента, что приводит к потере ссылки)**
```C++
void f(const int &data) { std::cout << "In thread: " << &data << std::endl; }

int main() {
  int x = 10;
  int &data = x;
  std::thread t(f, data);
  t.join();
  std::cout << "In main thread: " << &data << std::endl;
  return 0;
}
// Output
// In thread: 0x55bb0788ceb8
// In main thread: 0x7ffd057806b4
```

Решение кроется в функциях `std::ref()` и `std::cref()`, которые возвращают `std::reference_wrapper<T>` и `std::reference_wrapper<const T>`, которые в свою очередь умеют неявно преобразовываеться в `T&` и `const T&`, соответсвенно.

**Пример (Передача ссылки при помощи инструмента `std::cref`)**
```C++
void f(const int &data) { std::cout << "In thread: " << &data << std::endl; }

int main() {
  int x = 10;
  auto data = std::cref(x); // Явно приведение к std::reference_wrapper<const T>
  std::thread t(f, data);
  t.join();
  std::cout << "In main thread: " << &data.get() << std::endl;
  return 0;
}

// Output
// In thread: 0x7ffdba645184
// In main thread: 0x7ffdba645184
```

Важно помнить, что время жизни ссылки все еще контрлируется вызывающим кодом.

**Пример (Нарушение lifetime-жини ссылки (use-after-free))**
```C++
void f(int &data) {
  std::cout << "In thread: " << &data << std::endl;
}

int foo() {
  int x = 10;
  auto data = std::ref(x);
  std::thread t(f, data);
  t.detach();
  std::cout << "In main thread: " << &data << std::endl;
  return 0;
}
```


## Разбор кейсов

### Кейс №1
```C++
#include <string>
#include <thread>

void send_to_broker(const std::string& payload);
// Синхронно использует payload, ссылку после возврата не сохраняет.

void publish_event() {
    std::string payload = R"({"event":"order_created"})";

    std::thread worker(
        [](const std::string& message) {
            send_to_broker(message);
        },
        payload
    );

    payload.clear();
    worker.detach();
}
```

**Вопрос:** Есть ли здесь висячая ссылка или гонка данных из-за `payload.clear()` и выхода из `publish_event()`? Объясни, какой объект получает параметр `message` и как обеспечивается его время жизни.

**Ответ:** Нет, гонки данных нет, так как при передачи в поток объекта `payload` произойдет его копирование, и поток будет работать уже с копией данных `payload`. Параметр `message` ссылается на копию, созданную внутри потока. Поэтому очистка исходного объекта `payload` безопасна.

**Вопрос:** Коллега предлагает «убрать лишнее копирование», заменив последний аргумент конструктора потока на `std::cref(payload)`. Корректна ли такая оптимизация? Разбери отдельно время жизни и возможный одновременный доступ.

**Ответ:** Идея имеет несколько значительных проблем, во-первых, вопрос времени жизни, если поток запустится позже, чем произойдет выход из функции `publish_event` и уничтожение объекта `payload`, то мы получим `UB` (`use-after-free`)
Так же остается открытым вопрос гонки данных, если поток отработает после операции `payload.clear()`, то призойдет потеря данных

**Вопрос:** Требование: после запуска задачи исходная строка больше не нужна; её содержимое нужно передать фоновой задаче без копирования строки. Покажи минимальное изменение кода. Можно ли после такого изменения оставить `payload.clear()` и почему?

**Ответ:** Минимальное изменение кода
```C++
std::thread worker(
	[](const std::string& message) {
		send_to_broker(message);
	},
	std::move(payload) // std::move
);
```
