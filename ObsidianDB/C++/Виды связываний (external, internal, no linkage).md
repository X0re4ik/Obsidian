

Наша программа для компилятора одна большая книга, в ней есть главы, страницы, ссылки на другие главы и, конечно же, картинки.
Представим, что каждая глава для компилятора - это одна единица трансляции, в каждый главе может быть сслыка на другую главу.

Представим, что у нас есть 3 файла:

```bash
├── bar.cpp
├── foo.cpp
└── main.cpp
```

>`bar.cpp`
```C++
int sqr(int x) { return x * x; }
```

>`foo.cpp`
```C++
int sqr(int x);

bool check(int a, int b, int c) { return sqr(a) + sqr(b) == sqr(c); }
```

>`main.cpp`
```C++
#include <iostream>

bool check(int a, int b, int c);

int main() {
  std::cout << check(1, 2, 3) << std::endl;
  return 0;
}
```

Если мы скомпилируем приложение командой:
```
>> g++ -o main main.cpp foo.cpp bar.cpp
```
то программа успешно скомпилируется и выполниться, все потому что по умолчанию переменные в `C++` имеют  `external` связывание.


Взглянем на таблицу символов `bar.cpp`:

```
>> g++ -c bar.cpp -o bar.o
```

```
>> objdump -t bar.o


bar.o:     формат файла elf64-x86-64

SYMBOL TABLE:
0000000000000000 l    df *ABS*  0000000000000000 bar.cpp
0000000000000000 l    d  .text  0000000000000000 .text
0000000000000000 g     F .text  0000000000000013 _Z3sqri

```

Обратим внимание на значения из второй колонки -  `g` (`global`) и `l` (`local`) именно эти параметры и область видимости, в данном объектном файле функция `sqr` имеет глобальную область видимости, а значит будет доступна из вне даже при условии, что её и не планировалось использовать вызываемым кодом.

Зачем вообще мы заботимся об связываниях внутри наших единиц трансляции? Одна из причин - `ODR` (`One Definition Rule`)

Важно понимать разницу между *определением* и *объявлением* при работе с связыванием в контексте функций. Все функции по умолчанию имеют `external`

У каждой переменной и функции есть правило видимости:

1) Внешнее связывание

По умолчанию все *глобальные переменные* и *объявления функций* имеют внешнее связывание (`external linkage`)
Любое объявление внутри `.hpp` - потенциальная ошибка `ODR`. Привидём несколько примеров:

```C++
// bar.hpp

int x;
int *y;
thread_local int z; // Поговорим о нем чуть позже
const int* u; // Интересный кейс работы с const

int foo() { return 1; }
```

Все переменные из списка выше будут встроены в единицу трансляции (объектный файл) и, что для нас самое критичное, будут глобальными в таблице символов (`objdump -jC`)

```bash
0000000000000000 g     O .bss   0000000000000004 x
0000000000000008 g     O .bss   0000000000000008 y
0000000000000000 g       .tbss  0000000000000004 z
0000000000000010 g     O .bss   0000000000000008 u
0000000000000000 g     F .text  000000000000000f foo()
```

Когда мы говорим об архитектуре нашего приложения, нам интуитивно хочется, чтобы наши программы соответсвовали принципу `Open/Close` - поэтому стараемся отдавать во внешний мир только то, что реально необходимо в работе программы. 

Данная функция/переменная будет видна всем другим единицам трансляции

2) Внутреннее связывание

Интуитивно понятно, что если есть внешнее связывание, то будет и внутреннее, это противоположность внешнему. При внутреннем связывании объекты внутри единицы трансляции недоступны для других единиц трансляции

Исторически добиться внутреннего связывания в `C++` можно было при помощи `static`

```C++
// bar.hpp
static int x;
static int *y;
static thread_local int z;
static const int* u;

static int foo() { return 1; }
```


Волшебное ключевое слово `static` сделало все наши переменные внутренними, теперь всякий раз, когда мы выполняем `#include <bar>`  
```bash
0000000000000000 l     O .bss   0000000000000004 x
0000000000000008 l     O .bss   0000000000000008 y
0000000000000000 l       .tbss  0000000000000004 z
0000000000000010 l     O .bss   0000000000000008 u
0000000000000000 l     F .text  000000000000000f foo()
```


Данная функция/переменная будет видна только в рамках своей единице трансляции

3) Отсутствие связывания

Сущность существует только в рамках одного блока
