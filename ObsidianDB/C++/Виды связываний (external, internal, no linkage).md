
## Введение

Если вы когда-нибудь компилировали `C++`, то практически наверника получали ошибку формата 
```
main.cpp:4:6: error: redefinition of ‘void bar()’
    4 | void bar() {}
      |      ^~~
main.cpp:3:6: note: ‘void bar()’ previously defined here
    3 | void bar() {}
```

Наша программа для компилятора одна большая книга, в ней есть главы, страницы, ссылки на другие главы и, конечно же, картинки.
Представим, что каждая глава для компилятора - это одна единица трансляции, в каждый главе может быть сслыка на другую главу.

Представим, что у нас есть 3 файла:

```bash
├── bar.cpp
├── foo.cpp
└── main.cpp
```

>`bar.cpp`
```C++
int sqr(int x) { return x * x; }
```

>`foo.cpp`
```C++
int sqr(int x);

bool check(int a, int b, int c) { return sqr(a) + sqr(b) == sqr(c); }
```

>`main.cpp`
```C++
#include <iostream>

bool check(int a, int b, int c);

int main() {
  std::cout << check(1, 2, 3) << std::endl;
  return 0;
}
```

Если мы скомпилируем приложение командой:
```bash
>> g++ -o main main.cpp foo.cpp bar.cpp
```
то программа успешно скомпилируется и выполниться, все потому что по умолчанию переменные в `C++` имеют  `external` связывание.


Взглянем на таблицу символов `bar.cpp`:

```bash
>> g++ -c bar.cpp -o bar.o
```

```bash
>> objdump -t bar.o


bar.o:     формат файла elf64-x86-64

SYMBOL TABLE:
0000000000000000 l    df *ABS*  0000000000000000 bar.cpp
0000000000000000 l    d  .text  0000000000000000 .text
0000000000000000 g     F .text  0000000000000013 _Z3sqri

```

Обратим внимание на значения из второй колонки -  `g` (`global`) и `l` (`local`) именно эти параметры и область видимости, в данном объектном файле функция `sqr` имеет глобальную область видимости, а значит будет доступна из вне даже при условии, что её и не планировалось использовать вызываемым кодом.

Зачем вообще мы заботимся об связываниях внутри наших единиц трансляции? Одна из причин - `ODR` (`One Definition Rule`)

Важно понимать разницу между *определением* и *объявлением* при работе с связыванием в контексте функций. Все функции по умолчанию имеют `external`



У каждой переменной и функции есть правило видимости:

1) Внешнее связывание

По умолчанию все *глобальные переменные* и *объявления функций* имеют внешнее связывание (`external linkage`)
Любое объявление внутри `.hpp` - потенциальная ошибка `ODR`. Привидём несколько примеров:

```C++
// bar.hpp

int x;
int *y;
thread_local int z; // Поговорим о нем чуть позже
const int* u; // Интересный кейс работы с const

int foo() { return 1; }
```

Все переменные из списка выше будут встроены в единицу трансляции (объектный файл) и, что для нас самое критичное, будут глобальными в таблице символов (`objdump -jC`)

```bash
0000000000000000 g     O .bss   0000000000000004 x
0000000000000008 g     O .bss   0000000000000008 y
0000000000000000 g       .tbss  0000000000000004 z
0000000000000010 g     O .bss   0000000000000008 u
0000000000000000 g     F .text  000000000000000f foo()
```

Когда мы говорим об архитектуре нашего приложения, нам интуитивно хочется, чтобы наши программы соответсвовали принципу `Open/Close` - поэтому стараемся отдавать во внешний мир только то, что реально необходимо в работе программы.


2) Внутреннее связывание

Интуитивно понятно, что если есть внешнее связывание, то будет и внутреннее, это противоположность внешнему. При внутреннем связывании объекты внутри единицы трансляции недоступны для других единиц трансляции

Исторически добиться внутреннего связывания в `C++` можно было при помощи `static`

```C++
// bar.hpp
static int x;
static int *y;
static thread_local int z;
static const int* u;

static int foo() { return 1; }
```


Волшебное ключевое слово `static` сделало все наши переменные внутренними, теперь всякий раз, когда мы выполняем `#include "bar.hpp"`  -  произойдет копирование наших переменных в новую единицу трансляции, переменные будут локальными и для *каждой* единице трансляции *свои*

```bash
0000000000000000 l     O .bss   0000000000000004 x
0000000000000008 l     O .bss   0000000000000008 y
0000000000000000 l       .tbss  0000000000000004 z
0000000000000010 l     O .bss   0000000000000008 u
0000000000000000 l     F .text  000000000000000f foo()
```

3) Отсутствие связывания

Казалось бы, есть внутреннее и внешнее, что значит "нет связывания". По сути то и значит, объект (отмечу, что "объект", а не переменная или функция) не принадлежит ни одной единице трансляции.

```C++
class A {
private:
  int x;
};

typedef int IUCH;

enum Color {
  RED
};
```

Таблица символов для нашего файла будет невероятно скудная

```bash
SYMBOL TABLE:
0000000000000000 l    df *ABS*  0000000000000000 bar.cpp
```


Классы, структуры, перечисления, `typedef` и `using` не имеют связывания. Так как они не являются ....


`C++` не был бы `C++`, если бы на этом все и закончилось. Я предлагаю разобрать парочку интересных кейсов, которые случались на моей практике и практике моих коллег


Слабое связывание

```C++
struct Foo {
  static void foo() {}
};

void external_foo() { Foo::foo(); 
```

Ранее, мы говорили, что `static` приводит к объявлению функции локальной, но проблема в том, что в контексте использования классов `static` делает нас слабой ссылкой `w` в первой колонке

```
>> objdump -tC foo.o | awk '{print $2 "\t" $NF}'

l       foo.cpp
l       .text
l       .text._ZN3Foo3fooEv
w       Foo::foo()
g       external_foo()
```

Слабое связывание в контексе `C++` позволяет отдать выбор ссылки на откуп линковщику. У слабого свзывания есть неоспоримое преимущество и недостаток - преимущество в том, что линковщик выберет только 1 реализацию и именно ей будут пользоваться все остальные, но если по какой либо причине реализации отличаются - UB

Простой пример последнего случая

```C++
├── bar.cpp
├── foo.cpp
└── main.cpp
```

```C++
#include <iostream>

struct Foo {
  static void foo() { std::cout << "Я люблю оливки" << std::endl; }
};

void external_bar() { Foo::foo(); }
```

```C++
#include <iostream>

struct Foo {
  static void foo() { std::cout << "Я не люблю оливки" << std::endl; }
};

void external_foo() { Foo::foo(); }
```

```C++
void external_bar();
void external_foo();

int main() {
    external_bar();
    external_foo();
    return 1;
}
```

Мы уже знаем, что `external_bar` и `external_foo` являются внешними и будут нам доступны из основной программы, а вот `foo` вопрос не ясен, по итогу наша программа любит оливки, или предпочитает нечто иное...

Ответ кроется в то, *как* мы скомпилируем нашу программу

```bash
>> g++ main.cpp foo.cpp bar.cpp -o main
>> ./main
Я не люблю оливки
Я не люблю оливки

>> g++ main.cpp bar.cpp foo.cpp -o main
>> ./main
Я люблю оливки
Я люблю оливки
```

Одна и та же программа в зависимости от того, какую последовательность единиц трансляции мы задали работает совершенно по разному - вот вам и слабо связывание

Анонимность в `C++`

Ранее мы говорили о том, что в `C++` существует проблема с классам, перечислениями и typedef - все из-за того, что для линковщика это объекты без связывания, он считает, что в каждой единице трансляции одинаковая реализация объектов имеющих идентичное название
Но как же нам обойти это правило? Ответ кроется в `namespace {}` - анонимное пространство имён
Вспомним пример, с которого мы начали наш доклад
```C++

// bar.cpp
#include <iostream>
namespace {
struct Foo {
  void foo() { std::cout << "Я люблю оливки" << std::endl; }
};
} // namespace
void external_bar() {
  auto x = Foo();
  x.foo();
}

// foo.cpp
#include <iostream>
namespace {
struct Foo {
  void foo() { std::cout << "Я не люблю оливки" << std::endl; }
};
} // namespace
void external_foo() {
  auto x = Foo();
  x.foo();
}

// main.cpp
void external_bar();
void external_foo();

int main() {
    external_bar();
    external_foo();
    return 0;
}
```

Давайте посмотрим на примере `bar.cpp` из чего состояла функция до включения её в анонимный `namespace` и после

До:
```C++
#include <iostream>

struct Foo {
  void foo() { std::cout << "Я люблю оливки" << std::endl; }
};
void external_bar() {
  auto x = Foo();
  x.foo();
}
```

```
>> g++ -c bar.cpp -o bar.o
>> objdump -tC bar.o | grep "Foo::foo"
0000000000000000  w    F .text._ZN3Foo3fooEv    000000000000003e Foo::foo()
```

После:
```C++
#include <iostream>

namespace {
struct Foo {
  void foo() { std::cout << "Я люблю оливки" << std::endl; }
};
} // namespace
void external_bar() {
  auto x = Foo();
  x.foo();
}
```

```
>> g++ -c bar.cpp -o bar.o
>> objdump -tC bar.o | grep "Foo::foo"
0000000000000000 l     F .text  000000000000003a (anonymous namespace)::Foo::foo()
```

Мы видим, что по умолчанию `foo` была `external` и имела слабую связанность, но аннонимность позволила превратить `foo` в `internal`, что позволило избежать `ODR`, а так же наша позволило нашей программе наконец-то твердо и чётко заявить о своем отношении к оливкам
```bash
>> g++ main.cpp bar.cpp foo.cpp -o main
>> ./main
Я люблю оливки
Я не люблю оливки
```
