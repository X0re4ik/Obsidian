### Что такое mutex? Зачем он нужен? Как устроен?

`std::mutex` является одним из основных примитивов синхронизации потоков. Необходим `std::mutex`, в первую очередь, для устронение гонки данных. Верзнеуровнего `std::mutex` утроен при помощи механизмов `futex` и `CAS (Compare-And-Swap)`. Алгоритм следующий:

### Как правильно управлять блокировкой mutex? Что такое std::lock_guard и std::unique_lock? Чем они отличаются друг от друга?

`std::mutex` имеет методы `.lock()` и `.unlock()`, которые захватывают и освобождают мютекс, соотвественно. Но, если в промежутке между этими жвумя операциями произойдёт исключение, то мьютекс навсегда останется заблокированным. Чтобы этого избежать есть  `std::lock_guard` - это обёртка над `std::mutex`, которая придерживается идеомы `RAII`. `std::lock_guard` в своем конструкторе вызывает `.lock()`, а в деструкторе `.unlock()`. `std::unique_lock` похож на `std::lock_guard`, но может быть переиспользован, так как обладает методами `.lock()/.try_lock()` и `.unlock()`

### Что такое взаимная блокировка (deadlock)? Приведи пример ситуации, когда она может возникнуть. Как её избежать?

Взаимная блокировка - это ситуация, когда два и более потока заблокированы, потому что каждый из них ждет ресурс, занятый другим.

**Пример:**
```C++
strcut A {
	std::mutex m;
	int balance;
};

void transfer(A& to, A& from, int sum) {
	std::lock_guard alock{to.m};
	std::lock_guard block{from.m};
	
	to.balance += sum;
	from.balance -= sum;
}

// Поток 1
transfer(a, b, 100);
// Поток 2
transfer(b, a, 100);
```

В примере выше может возникнуть ситуация:
1) "Поток 1" заходит в transfer
2) "Поток 1" **захватывает** mutex объекта **a**
3) "Поток 2" заходит в transfer
4) "Поток 2" **захватывает** mutex объекта **b**

Далее ни "Поток 1" , ни "Поток 2" не могут выполняться, так как оба мьютекса a и b уже захвачены.

Единого правила по избегаю deadlock-нет, потому что они очень индивидуальны. Но можно придерживаться некоторых правил:

1) Единый порядок захвата
2) Использования `std::scoped_lock(m1, m2)` при захвате нескольких мьютексов
3) Короткие критические секции

### Что такое гонка данных (data race)? Чем она отличается от deadlock?

Гонка данных (`data race`) - это сценарий, когда несколько потоков пытаются записать данные без синхронизации своих действий. Типичный пример:
```C++
int g_counter = 0;

std::thread t1([&](){ ++g_counter; });
std::thread t2([&](){ ++g_counter; });
```

Если `deadlock` может полностью заблокировать работу прогаммы, то `data race` может привести к неопредленному поведению.

### Что произойдет, если объект std::thread будет разрушен, а поток не был ни joined, ни detached?

В деструкторе `std::thread` есть условие:
```C++
if (joinable()) std::__terminate();
```
Соотвестветсвенно, если мы не дождались `.join()` и/или не вызвали `.detached()`, то объект будет считаться `.joinable()` - программа заершится с `std::terminate`


## Сети

### 1. Модель OSI. Расскажи кратко про каждый уровень.

OSI - это концептуальная модель: делим сетевую комуникацию на 7 горизонтальных уроней, каждый решает только свою задачу и общается только с соседями сверху и снизу.

1) Физический - Самый нижний уровень. Отвечает за передачу сигналов в физической среде: по кабелям, оптоволокну, радиоволнам.
2) Канальный - Отвечает за передачу данных в пределах одной локальной сети, проверяет целостность данных, обнаруживает и исправляет ошибки.
3) Сетевой - Занимается маршрутизацией: определяет, по какому пути отправлять данные. Использует IP-адреса для поиска устройств в сети, отвечает за адресацию и доставку пакетов.
4) Транспортный - Обеспечивает передачу данных между приложениями. Разбивает большие объёмы информации на части и собирает их на стороне получателя.
5) Сеансовый - Управляет сессией связи: устанавливает, поддерживает и завершает соединение между устройствами, следит за синхронизацией передачи.
6) Представления - Преобразует данные в формат, понятный приложениям. Отвечает за сжатие, шифрование и кодирование информации. Например, превращает картинку в JPEG или текст в ASCII.
7) Прикладной - Самый верхний уровень. Взаимодействует с пользовательскими программами: браузерами, почтовыми клиентами, мессенджерами.

### 2. Модель TCP/IP. Расскажи кратко про каждый уровень.

TCP/IP - реальная модель: именно данная модель используется в обработке данных в сети. Она имеет значительно меньше уровней (4 против 7), а также допускает прокидывание данных между пакетами.

1) Канальный уровень - Устанавливает физическое соединение между устройствами в локальной сети с помощбю радиоволн и проводов
2) Межсетевой уровень - Строит маршруты между устройствами по всему интернету - этот процесс называется маршрутизацией
3) Транспортный уровень - Передача данных по маршруту, построенному на преддыдущем уровне
4) Прикладной уровень - Настраивает связи между приложениями (связь между браузером и серверным софтом)

### 3. Что такое сокет?

Сокет - это абстракция внутри ОС, с которой взаимодействует прикладная программа для общения по сети.
Существует несколько типов сокета:
* TCP - сокет - надёжная поставка данных с контрллем последовательности
* UDP - сокет - быстрая передача без гарантий поставки
* Unix - сокет - локальное взаимодействие между процессами на одной машине

Алгоритм работы с сокетами:
1) Сервер создаёт сокет и привязывает его к порту
2) Сервер переходит в режим прослушивания
3) Клиент создаёт сокет и подключается к серверу
4) Происходит обмен данными
5) Соединение закрывается

### 4. Что такое IP-адрес? Какая разница между IPv4 и IPv6?

IP-адрес - это уникальный адрес устройства в сети. С помощью IP-адреса устройства находят друг друга в сети и пересылают пакеты. IP адрес состоит из номера хоста и номера сети. На данный момент поддерживается и развивается 2 версии IP: IPv4 и IPv6

**IPv4:** 32-битное число, записывается как четыре десятичных октета 0–255 через точку (например, `234.34.87.23`). Адресное пространство всего 232≈4,32^{32} \approx 4{,}3232≈4,3 млрд адресов — оно давно исчерпано, из-за чего повсеместно применяется NAT, когда много устройств делят один публичный адрес .

**IPv6:** 128-битное число, записывается как восемь блоков по 16 бит в шестнадцатеричном виде через двоеточие, с возможностью сокращения нулей через `::` (например, `2001:db8:85a3::8a2e:370:7334`). Даёт 21282^{128}2128 адресов — NAT не нужен, каждое устройство может иметь глобальный адрес .

**Ключевые различия IPv6:** огромное адресное пространство; упрощённый заголовок фиксированной длины без контрольной суммы и без полей фрагментации (маршрутизаторы пакеты не фрагментируют — это делает отправитель через ICMPv6); нет broadcast — вместо него multicast; автоконфигурация адресов через SLAAC без DHCP; изначальная интеграция с IPsec (хотя IPsec доступен и в IPv4).

### 5. Что такое маска подсети? Зачем нужна маска подсети?

Маска подсети делит IP адрес на адрес сети и адрес узла, а также позволяет разбить большую сеть на более мелкие. Маска необходима для того, чтобы устройства в сети понимали, как общаться между собой - через шлюз или напрямую (по протоколу ARP)

Если устройства находтся в одной сети, то они минуют маршрутизатор и общаются друг с другом напрямую, если же в разных, то устройство шлёт пакет на так называемый хот шлюза, пакет попадает маршрутизатору и уже он перенаправляет его в другю сеть.

### 6. Что такое порт? Зачем он нужен?

Порт представляет из себя униклаьный идентификатор точки на хосте, который сейчас производит общение. Верхнеуровнего можно связать порт с конкретным процессом, который его слушает или использует. Разделение на порты позволяет несколким программам общаться по сети с одного устройства. В TCP протоколе идентификатор соединения характерезуется четвекой: IP dst/Port dst/IP src/Port src

### 7. Расскажи про протокол IP.

IP - протокло относится к сетевому уровню модели OSI, то есть к третьему уровню. IP протокол служит для передачи пакетов в сети между утройствами. Размер заголовка IP протокола вариаруется от 20 до 60 байт (в зависимости от опций), но всегда содержат IP отправителя и IP получателя. Стоит отметить, что IP протокол никаких гарантий не дает: нет контроля доставки, проверки соединения - все это обязанность более прикладных протоклово (UDP; TCP)

Внутри IP протоклоа есть множество заголовков:
- TTL (защита от зацикливания) - проходя через шлюз значение уменьшается на 1 и пересчитывается контрольная сумма заголовка
- Protocol - информация по протоколу, который используется внутри пакета (UDP; TCP и т.д.)
- Версия протокола
- Размер пакета
- IP адрес получателя
- IP адрес отправителя

### 11. Расскажи про протокол TCP.

TCP - это пртокол передачи данных между устройствами. Находится на 4-ом (транспортном) уровне модели OSI. Основная особенность и премущество - гарантированная доставка сгементов (пакетов). Большиство прикладных протоколов постренно на основе TCP: HTTP/1/2; WebSocket; FMTP; SSH; Telnet; LDAP и др.
Имеет узкое горлышко в виде HOL-блокировки.

### 12. TCP. Как происходит установление соединения? Что такое TCP handshake?

TCP соединение устанавливается в 3 этапа: `SYN -> SYN + ACK -> ACK`
1) Клиент отправляет специальный флаг на установку соединения `SYN`
2) Сервер отвечает запросом на соединение и ответом на принятие соединения: `SYN + ACK`
3) Клиент отвечает, что готов принять соединение сервера: `ACK`

### 13. TCP. Как происходит контроль скорости передачи данных?

TCP протокло контролирует скорость передачи данных при помощи двух механизмов:
* Контроль перегрузки (Congestion Control)
Данный метод защиты впервые был реализован при помощи алгоритма Reno. Основная кего задача 0 обеспечить максимальную скорость передачи данных в сети. Алгоритм Reno строится на 4-ёх фазах:
1) Slow Start (медленный старт) - сначала в сеть отпрявлеятся небольшой сегмент
2) **TODO**
* Управление потоклом (Flow Control)
Предотвращает отправку слишком большого количества данных получателю. Каждая сороная TCP соединения сообщает о максимальном размере буффера для поступающих данных - окно скольжение.

### 14. TCP. Что такое окно скольжения?

Для опредление окна скольжения необходимо опредлеить размер окна.
Размер окна - количество байт, которые могут быть переданы без подтверждения.
Окно скольжения предполагает отправку нескольких сегментов одновременно, после подтверждения блока сегментов - окно сдивгается и в сеть отправляются следующие несколько сегментов - это позволяет принимающей стороне отвечать на запросы камулятивно.

### 15. TCP. Как происходит обнаружение и исправления ошибок?

В TCP есть две группы ошибок:

1) Потеря сегментов в сети
Сегменты в сети могут терятся, в таких ситуациях клиент имеет timeout на получение подтверждения сегмента. Если по истечению timeout-а сегмент так и не был подтверждён - клиент переотправляет сегмент в сеть

2) Повреждение данных в сети
В заголовке TCP имеется контрольная сумма сегмента, она позволяет отловить ситуации, когда сегмент пришёл битым и молча проигонрировать его

### 16. TCP. Как происходит закрытие соединения? Что такое состояние TIME_WAIT и почему оно может быть проблемой в проде?

Закрытие TCP соединения происходит в 4 этапа:
1) Клиент отправляет флаг о завершении отправки данных - флаг **FIN**
2) Сервер отправляет флаг **ACK** клиенту и доотправляет необходимые данные клиенту 
3) После завершения отправки всех данных сервер отправляет также флаг **FIN**
4) Клиент получает флаг FIN от сервера и отправляет свой **ACK**

Проблема находится после 4-ого шага, а именно в момент, когда клиент находится в состоянии **TIME_WAIT**. Почему клиент вынужден ждать 2xMSL (около минуты на Linux) перед тем, как закрыть соединение? Есть две фундаментальные проблемы:
1) Ожидаение всех "заблудих" сегментов. Если сразу же закрыть соединение, то новое соединение может получить сегмент старого соединения (помним, что сегменты идентифицируются четверкой - IP source/Port source - IP dist/Port dist)
2) Гарантированная доставка ACK до сервера. Если ACK клиента потеряется в сети, то через некоторое время сервер пришлёт повторный FIN, а клиент повторно отправит ACK

Из-за этого ожидания в 2xMSL клиент вынужден держать неиспользуемый порт, что в при множестве запросов на машине клиента может привести к исчерпанию эфемерных портов.

### 17. Что такое алгоритм Нейгла (Nagle's algorithm)? Как он связан с флагом TCP_NODELAY?

Алгоритм Нейгла решает проблему "небольших" пакетов, алгоритм предотварщает отправку небольших сегментов, накапливая их для отправки большого более значительного сегмента серверу, чтобы уменьшить нагрузку на сеть. Более детальная работа алгоритма следующая:
1) Если нет неподтвержденных сегментов - отправка даже небольшого сегмента
2) Если есть неподтвержденные сегменты - буфферизация сегментов, пока не придёт ACK или не наберется полный MSS

Но алгоритм Негла (который использует клиент) вступает в конлфикт с алгоритмом Delayed ACK (отложенное подтверждение). Сервер не отвечает сразу же на сегмент, а дожидается нескольких из них, чтобы ответить ACK на несколько сразу.

TCP_NODELAY - это опция, которая отключает алгоритм Нейгла. Позволяя со стороны клиента не буфферизировать сегменты и отправлять их сразу. Напрмиер, в протоколе gRPC эта опция включена по умолчанию, чтобы снизить все сегменты немедленно были отправлены серверу.

### 18. Расскажи про протокол UDP.

UDP - это пртокол передачи данных между устройствами. Находится на 4-ом (транспортном) уровне модели OSI. Основные отличия от TCP: отправка датаграмм вместо потока данных, отсутвие гарантии доставки датаграм.
UDP в привычном понимании асициируется сос коорстью - меньший размер заголовка, отсутвие требований к подтверждения. Среди современных прикладых протоклов UDP можно встретить: HTTP/3; DNS; WebRTC; QUIC; OpenVPN

### 20. Зачем нужен UDP, если есть TCP?

За время существования TCP он пережил множество изменений. Почему может быть полезен UDP:
1) Скорость - TCP соединение требует подвержления пакетов, если один из пакетов оказался битым или потерялся - весь поток байт встает в буффер в ожидании этого пакета (HOL-блокировка на уровне TCP)
2) Границы сообщений - каждая датаграмма это одно полноценное сообщение без разделений.
3) Компактность, заголовок UDP сообщений - 8 байт, у TCP - минимум 20 байт

Отметим, что HTTP/3 использует QUIC поверх UDP. QUIC самостоятельно обеспечивает надёжную доставку внутри потоков, но потеря данных одного потока не требует останавливать выдачу данных других независимых потоков.

### 21. Какие гарантии даёт UDP?

UDP, в отличии от TCP, не дожидается ответа от сервера, он лишь отправляет данные по адресу, но без специализированных протоколов поверх (например, QUIC) не гарантирует доставку, то есть пакеты отправленные UDP могут не дойти, потеряться, прислаться повторно. Единственная проверка - проверка контрольной суммы, но она нужна только, чтобы отбросить сервером "испорченные" пакеты.

Но есть также и отличительная черта UDP - границы сообщений. UDP отправляет данные датаграммами. Если в одной датаграмме написано "hello", а во второй " world", то клиент получит их в полном объеме. В TCP же клиент может вычитать сначала "he", потом "llo" - рагарничение это отвественность прикладного приложения.

### 22. Что будет, если два хоста решили установить соединение и номера портов с одной и другой стороны совпадают?

Ничего страшного не произойдет. Каждое TCP соединение идентифицируется четверкой: IP отправителя, порт отправителя, IP получателя, порт получателя. У них будут разные IP получателя и отправителя, что не вызовет конфликтов в сети (как будто бы 2 запроса друг другу). Более того, TCP поддерживает **simultaneous open** - одновременное открытие, при котором будет открыто не два соединения, а одно двухнапрвленное.

### Допустим установлено соединение по TCP, отправляется слово hello, 5 байт. Что может увидеть принимающая сторона? Могут ли буквы прийти в другом порядке? Могут ли буквы поменяться, например, вместо h будет r? То же самое верно для UDP?

**TCP:**
- Могут ли буквы прийти в другом порядке? - **НЕТ**
TCP стек обрабатывает поток байтов. Принимающее приложение получает байты в порядке отправки, но может читать их частями. Для получения полного сообщения приложение должно само определить его границы и прочитать необходимое количество байтов.
- Могут ли буквы поменяться? - **ДА**
В процессе отправки пакеты могут приходить не по порядку - это нормальное поведение для TCP стека, такие пакеты складываются в буффер, чтобы дождатся полной цепочки последовательнсоти пакетов. Пакеты также могут иметь ошибки и повреждения в процессе передачи, чтобы ичключить эти ошибки есть механизм контрольной суммы - который позволяет отклонять поврежденные пакеты. Но механизм контрольной суммы не абслютная гарантия. Теоретически у двух пакетов с разным содержимым может быть одна контрольная сумма - что привидет к неправильному вычитыванию пакета.

**UDP:**
- Могут ли буквы прийти в другом порядке? - **ДА**
Проблема в том, что UDP читается датаграммами. Если киент отправил 5 байт 5-ю разными датаграммамит, то вполне возможно, что сервер не получит часть данных, а часть данных придут не в той полседовательности.
- Могут ли буквы поменяться? - **ДА**
У UDP также есть мехнизм контрольной суммы, который подтверждает целостность данных, это не абслютная гарантия, так как контрольная сумма у двух совершенно разных пакетов может быть идентичной. Так что полной гаранитии целостности данных стек дать не может. Практически, если клиент отправил датаграмму из 5 байт с контрольной суммой N, а сервер получил эту датаграмму с 5 другими байтами, а контрольная сумма попрежнему N - UDP не отклонит эту датаграмму, а продолжит с ней работать.


### Какое количество IP адресов можно поднять на сетевой карте? Один или несколько?

Теоретически огранения нет, на одном и том же интрефейсе может быть несколько IP адресов. Можно самостоятельно интерфейсу присвоить новый IP адрес: `ip addr add`

**Пример**
```bash
sudo ip addr add 192.168.1.10/24 dev eth0
sudo ip addr add 192.168.1.11/24 dev eth0
```

### Сколько у роутера/маршрутизатора может быть IP адресов?

Задача роутера/маршрутизатора (далее Р/М) - перенаправлять пакеты от отправителя к получателю. Если компьютер видит IP адрес не в своей сети - от отправляет его Р/М, таким образом компьютеру достаточно значть только 1 адрес Р/М, но сам Р/М могут находится в N подсетях (в том числе и подсети провайдера). Адреса в Р/М назначаются его интерфейсам, соотвественно, на одном интерфейсе может быть несколько IP адресов. Для домашней сети достаточно обычно двух - один в LAN-сети, второй в WAL-сети. 

### Допустим мы подключились к роутеру по проводу и по Wi-Fi. По какому из этих интерфейсов пойдёт пакет?

Если у нас 2 способа передачи пакетов: WiFi и Ethernet, то ОС выбирает приоритетный путь по специфики маршрута и **метрикам**.

Метрика - это число, которое присвоивается каждому из маршрутов, чем меньше это число - тем приоритетней способ передачи даннх.

Специфика маршрута - если для конечного IP имеется более предпочтительный путь с большей метрикой, то ОС выберет именно его. 

Посмотреть список способов и их метрики можно при помощи команды `ip route show`

**Пример:**
```bash
ip route show

default via 192.168.0.1 dev wlo1 proto dhcp metric 600 
169.254.0.0/16 dev wlo1 scope link metric 1000 
172.17.0.0/16 dev docker0 proto kernel scope link src 172.17.0.1 
172.18.0.0/16 dev br-57f33f3cf2aa proto kernel scope link src 172.18.0.1
```

В примере выше видно, что по умолчанию приоритет отдается wi-fi соединению (метрика 600, признак `wlo1`), то есть при отправке данных на IP 8.8.8.8 пакеты пойдут через `wi-fi`, но если я хочу обратиться к `docker`  по ip  `172.17.0.2`, то приоритет будет у сети `docker0`, так как она более специфична.


### Что такое NAT? Зачем он нужен? Как он влияет на количество IP-адресов, видимых снаружи сети?

NAT (Network Address Translation) - это технология, которая заменяет IP адрес отправлителя при их прохождении через маршрутизатор. NAT - это спасение в условиях ограниченности IP адресов. Есть 3 способа использования NAT:

- Статический - 1 публичный IP ссылается на 1 локальный IP
- Динамический - пулл публичных IP адресов присваивается пулу публичных локальных адресов
- PAT или NAT Overload - самый распостраненный вариант, когда публичный IP адрес не изменяется, а меняется порт на маршрутизаторе и IP отправителя (см. пример)

NAT позволяет скрыть множество различных IP адресов за 1 или несколькими публичными IP адресами.

**Пример:**
```
До трансляции              После трансляции
192.168.1.10:50000    →     203.0.113.5:50000
192.168.1.11:50000    →     203.0.113.5:50001
```


### Что такое TLS/SSL? Как происходит TLS handshake? Сколько RTT он добавляет по сравнению с обычным HTTP?

TLS/SSL - это протокло установения "безопасного" соединения между клиентом и сервером. TLS handshake состоит из нескольих этапов согласования финального зазищенного ключа. Рассмотрим пример установления соединения на TLS 1.3:
1) Клиент посылает запрос (Client Hello), в которм указывает поддерживаемые версии, алгороимы и свой `key_share`
2) Сервер отвечает (Server Hello) версией, которая будет использоваться, своим  `key_share`, а также сенртификатами, чтобы клиент мог удостоверится в подлиности сервера. На этом же этапе сервер отправляет **FINISHED** - знак, что TLS соединение успешно устанволено

На этом эатпе каждый из участников генериуют общий секрет на основании открытого ключа собеседника и своего приватного ключа

3) Клиент проверяет сертификаты, если все корректно, то отправляется **FINISHED** клиента

На анный момент можно считать, что TLS соединение между клиентом и сервером установлено.

RTT зависит от версии, если версия ниже 1.3, то RTT будет равен двум, если 1.3, то 1. TLS 1.2 отправлял свой `key_share` отдельным запросом из-за чего появлялся лишнйи RTT.

### 29. В чем отличие HTTP/1.1, HTTP/2 и HTTP/3? Как HTTP/3 (QUIC) сокращает число RTT на установление соединения?

HTTP/1 появился на заре интернета - он описал общие правила работы между браузером и сервером по HTTP. Всем привычные и знакомые GET; POST; Headers и Body появились в нем.

Но у HTTP/1 был одна большая проблема - HOL блокировка на уровне HTTP, если мы запрашивали js файл и css файл с одного источника (домена), то пока нам не вернут js файл, сервер не станет обрабаотывать получение css файла, что приводило к задержкам.

HTTP/2 решил эту проблему введя понятие **stream_id** и делением данных на фреймы - мультеплексирование. Это позволило нам однозначно разделять запросы между собой и обрабатывать уже собранные пакеты по **stream_id**.
HTTP/2 все еще очень хорош по производительности и скорости, многими любимый gRPC работает поверх HTTP/2.

Но  HTTP/2 не решает HOL-блокировки на уровне TCP. Если один из пакетов потеряется, то блокируется все **stream_id** до того момента, пока потерянный пакет не вернется. Также росло количество модильных устройств и появилось требование к востсановлению сети: клиент идет из точки A в точку B, меняется поставщик сети, у клиента резко меняется IP адрес - для TCP стека это однозначна разрыв соединения и заного устанволения соединения

HTTP/3 решил эти проблемы:
- Каждый запрос ресурса независим. Мы запросили css; js; json. Данные по css потерялись, но js и json мы можем обработать - возвращает ответ
- Введение понятия connection id - в рамках соединения клиент и сервер договоривются о connection id - идентификаторе соединения. Это позволяет восстанавливать соединения в случаи смены IP или прерывания.
- 1 RTT на установку TLS соединения. Исторически HTTP/1 и HTTP/2 необходимо минимум 2 RTT: соединение + обмен ключами. В QUIC TLS1.3 заложиди на уровне протокла и отправка ключей идет вместе с первым SYN

### 30. Есть холодный HTTPS запрос. Какой минимальный RTT требуется для получения 1 байта в ответ?

Первым делом нам необходимо установить соединение - это займет 1 `RTT` (`SYN -> SYN/ACK -> ACK`), далле минимум 1 RTT потребуется для установки `TLS` соединения, и 1 `RTT` на получение байт.

Соотвественно, холодный `HTTPS` запрос потребует минимум 3 `RTT`.
