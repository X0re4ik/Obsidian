
## Что такое паттерн проектирования? Зачем они нужны? Какие категории паттернов ты знаешь?

Паттерн проектирования - это паттерны посторения архитектуры приложения для решения типовых задач программирования. Необходимы они в первую очередь для того, чтобы из них выстраивать понятные, тестируемые программы.
Паттерны деляется на несколько каттегорий:
1) Порождающие - управляют созданием объектов и скрывают детали их инстанцирования. Они помогают уменьшить зависимость кода от конкретных классов и делают создание объектов более гибким. Примеры: Factory Method, Abstract Factory, Builder, Prototype, Singleton.
2) Структурные - описывают, как объединять классы и объекты в более крупные, но гибкие структуры. Примеры: Adapter, Decorator, Facade, Composite, Proxy, Bridge.

## Что такое паттерн Singleton? Какие проблемы он создаёт, в том числе в многопоточном коде?

Пример реализации Singleton стандартной версии и Скотта Мейерса:
```C++
class ExampleSingleton {
public:
  ExampleSingleton(const ExampleSingleton &) = delete;
  ExampleSingleton &operator=(const ExampleSingleton &) = delete;
  ExampleSingleton(ExampleSingleton &&) = delete;
  ExampleSingleton &operator=(ExampleSingleton &&) = delete;

  static ExampleSingleton &getInstance(std::string name) {
    std::lock_guard<std::mutex> lock(mtx_);

    if (!instance_) {
      instance_ = std::unique_ptr<ExampleSingleton>(
          new ExampleSingleton(std::move(name)));
    }

    return *instance_;
  }

  void doSome() const {
    std::cout << std::this_thread::get_id() << " - " << name_ << '\n';
  }

private:
  explicit ExampleSingleton(std::string name) : name_(std::move(name)) {}

  ~ExampleSingleton() = default;

  static std::unique_ptr<ExampleSingleton> instance_;
  static std::mutex mtx_;

  std::string name_;
};

// Обязательная инициализация
ExampleSingleton *ExampleSingleton::instance_ = nullptr;
std::mutex ExampleSingleton::mtx_;

class MeyersSingleton {
  /**
   * @brief Пример синглтона Скотта Мейерса
   *  Объект создается на месте, что начиная с C++11 потокобезопасно
   */
public:
  MeyersSingleton(const MeyersSingleton &) = delete;
  MeyersSingleton &operator=(const MeyersSingleton &) = delete;
  MeyersSingleton(MeyersSingleton &&) = delete;
  MeyersSingleton &operator=(MeyersSingleton &&) = delete;

  static MeyersSingleton &getInstance(std::string name) {
    static MeyersSingleton instance_(std::move(name));
    return instance_;
  }

  void doSome() {
    std::cout << std::this_thread::get_id() << " - " << name_ << '\n';
  }

private:
  explicit MeyersSingleton(std::string name) : name_(std::move(name)) {}
  ~MeyersSingleton() = default;

  std::string name_;
};

void ThreadBar(std::string name_) {
  // ExampleSingleton / MeyersSingleton
  MeyersSingleton::getInstance(name_).doSome();
}

int main() {

  auto t1 = std::thread(ThreadBar, "t1");
  auto t2 = std::thread(ThreadBar, "t2");

  t1.join();
  t2.join();

  return 0;
}
```

Недостатки Singleton:
1) Глобальное состояние
Глобальное состоние, означает, что любой другой класс может изменить состояние объекта Singleton, отледить, кто именно изменил состояние и к какаим последствям это привело может быть крайне проблематично
2) Гонка данных
Гонка при создании экземпляра, если Singleton не является Meyers Singleton или не использует блокировку потоков, то можно легко получить состояние, в котором 2 потока пытаются создать объект Singleton
3) Сложность тестирования
Singleton представляет собой глобальное состояние, а значит при тестировании очень тяжело провести работу Singleton изолированного от других частей приложения




## Что такое паттерн Factory Method? Чем он отличается от Abstract Factory и от Builder?

Паттерн Factory Method
```C++
class IProduct {
public:
  virtual ~IProduct() = default;

  virtual void Do() const = 0;
};

class AProduct final : public IProduct {
public:
  AProduct(int id, std::string name) : id_(id), name_(std::move(name)) {}

  void Do() const override {
    std::cout << "AProduct: id = " << id_ << ", name = " << name_ << '\n';
  }

private:
  int id_;
  std::string name_;
};

class BProduct final : public IProduct {
public:
  explicit BProduct(std::string name) : name_(std::move(name)) {}

  void Do() const override {
    std::cout << "BProduct: name = " << name_ << '\n';
  }

private:
  std::string name_;
};

class ProductCreator {
public:
  virtual ~ProductCreator() = default;

  virtual std::unique_ptr<IProduct> factoryMethod() const = 0;

  void someDo() const {
    auto product = factoryMethod();
    product->Do();
  }
};

class AProductCreator final : public ProductCreator {
public:
  std::unique_ptr<IProduct> factoryMethod() const override {
    return std::make_unique<AProduct>(1, "AProduct");
  }
};

class BProductCreator final : public ProductCreator {
public:
  std::unique_ptr<IProduct> factoryMethod() const override {
    return std::make_unique<BProduct>("BProduct");
  }
};

void doProduct(const ProductCreator &creator) { creator.someDo(); }

int main() {
  BProductCreator creator;
  doProduct(creator);
}
```

Зачем применять Factory Method?
Типичный сценарий использования: Есть несколько продуктов, которые содержат один и тот же метода, но работают с разным набором данных. Класс `Creator` опредляет метод `factoryMethod`, который позволяет создасть необходимый объект, а соседний метод `someDo` опреляет бизнес логику работы с продуктом.

Отличие от Abstract Factory и Builder:
1) Builder применяют, когда объект сложный, имеет много необязательных параметров или создаётся поэтапно. Он отделяет процесс построения от итогового объекта.
2) Abstract Factory похожа по сути, но решает немного иную задачу, Abstract Factory создает семейство связанных и совместимых продуктов. Типичный пример: кнопки и баттоны разного цвета

## Что такое паттерн Observer? Приведи пример использования.

Пример Observer
```C++
class IHandler {
public:
    virtual ~IHandler() = default;

    virtual void notify() = 0;
};

class AHandler final : public IHandler {
public:
    void notify() override {
        std::cout << "AHandler received notification\n";
    }
};

class BHandler final : public IHandler {
public:
    void notify() override {
        std::cout << "BHandler received notification\n";
    }
};

class Subject {
public:
    explicit Subject(std::vector<std::unique_ptr<IHandler>> handlers)
        : handlers_(std::move(handlers)) {}

    void notify() {
        for (const auto& handler : handlers_) {
            handler->notify();
        }
    }

private:
    std::vector<std::unique_ptr<IHandler>> handlers_;
};

int main() {
    std::vector<std::unique_ptr<IHandler>> handlers;

    handlers.push_back(std::make_unique<AHandler>());
    handlers.push_back(std::make_unique<BHandler>());

    Subject subject(std::move(handlers));
    subject.notify();
}
```

Зачем применять Factory Method?
Пример использования Observer из работы: У нас есть такое событие "Создание итерации", как только оно приходит из Kafka - оно запскает несколько операций:
1) Очистка данных по предыдущей итерации
2) Отправка логов в сервис аудита
3) Пересчёт значений
Вся работа по событию реализована через паттерн Observer, есть внешний `notify`, который запускает `notify` для всех подписывшихся обработчиков


## Что такое паттерн Strategy? Чем он отличается от паттерна Decorator?

Пример Strategy
```C++
class IStrategy {
public:
  virtual ~IStrategy() = default;

  virtual void doOperation() const = 0;
};

class AStrategy final : public IStrategy {
public:
  void doOperation() const override { std::cout << "Strategy A\n"; }
};

class BStrategy final : public IStrategy {
public:
  void doOperation() const override { std::cout << "Strategy B\n"; }
};

class Context {
public:
  explicit Context(std::unique_ptr<IStrategy> strategy)
      : strategy_(std::move(strategy)) {
    if (!strategy_) {
      throw std::invalid_argument("Strategy must not be null");
    }
  }

  void doSome() const { strategy_->doOperation(); }

  void updateStrategy(std::unique_ptr<IStrategy> strategy) {
    if (!strategy) {
      throw std::invalid_argument("Strategy must not be null");
    }

    strategy_ = std::move(strategy);
  }

private:
  std::unique_ptr<IStrategy> strategy_;
};
```

Зачем применять Strategy?
Strategy применяют, когда есть несколько взаимозаменяемых способов выполнить одну задачу. Каждый алгоритм выносится в отдельный класс с общим интерфейсом, а Context получает и использует выбранную стратегию. Это позволяет менять алгоритм без изменения Context. Например, есть единый сервис расчёта стоимости доставки. Он принимает одну из возможных стратегий расчёта: курьерскую, экспресс-доставку или самовывоз. Сам сервис не содержит логику расчёта в виде большого `if/else`, а только вызывает выбранную стратегию. Каждая конкретная стратегия инкапсулирует собственные правила расчёта.

Отличие от Decorator:
Стратегия меняет в целом алгоритм расчёта и логику работы, декоратор же является оберткой для уже сущесвьующего функционала, что позволяет декоратору изменять поведение вокруг объекта.

## Что такое паттерн Adapter? Чем он отличается от паттерна Facade?

```C++
class IRequest {
public:
  virtual ~IRequest() = default;

  virtual void doRequest() = 0;
};

class FileRequest {
public:
  void doFileRequest() { std::cout << "File request executed\n"; }
};

class FileRequestAdapter final : public IRequest, private FileRequest {
public:
  void doRequest() override { doFileRequest(); }
};

void processRequest(IRequest &request) { request.doRequest(); }

int main() {
  FileRequestAdapter adapter;

  processRequest(adapter);
}
```

Зачем применять Adapter?
Adapter применяют, когда есть готовый класс с нужной функциональностью, но его интерфейс несовместим с интерфейсом, который ожидает клиентский код. Adapter реализует целевой интерфейс клиента и внутри преобразует вызовы в формат, понятный адаптируемому классу. Adapter реализуется через наследование или композицию.

Отличие от Facade:
Facade дает понятный интерфейс, который скрывает за собой сложную бизнес логику состояющую из нескольких различных операций. Например: клиент получает простой метод `send`, который в реализации вызывает 5 методов различных классов и структур
Adapter не упрощает подсистему и не объединяет несколько операций ради удобства. Он преобразует один несовместимый интерфейс в другой, уже ожидаемый клиентским кодом.
