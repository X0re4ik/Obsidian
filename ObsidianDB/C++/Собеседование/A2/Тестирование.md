
## Что такое тестирование? Зачем оно нужно?

Тестирование - процесс проверки программы и её поведения на заранее выбранных сценариях. Оно помогает выявлять дефекты, проверять соответствие требованиям и снижать риск регрессий при изменениях.

## В чем отличие юнит-тестов от интеграционных тестов?

**Unit-тестирование** проверяет небольшой изолированный фрагмент кода: функцию, класс или компонент. Внешние зависимости обычно заменяются заглушками, поэтому тесты быстрые и локализуют причину ошибки.

**Интеграционное тестирование** проверяет взаимодействие нескольких компонентов или системы с внешней зависимостью: БД, Kafka, HTTP-сервисом. Важно убедиться, что данные корректно передаются и читаются на границе интеграции.

## Что такое mock-тест?

Mock - объект-подмена, который имитирует зависимость и позволяет проверить взаимодействие с ней: какие методы вызваны, с какими аргументами и сколько раз. Mock-тестом обычно называют unit-тест, использующий такую подмену.

Для удобного mock-тестирования зависимости выделяют за интерфейсами и делают небольшими. Это упрощает замену реальной БД, очереди или сервиса на mock.

**Пример mock тестирования на `GoogleTest`**
```C++
#include <gmock/gmock.h>
#include <gtest/gtest.h>

#include <string>

class IEmailSender {
public:
    virtual ~IEmailSender() = default;

    virtual bool send(
        const std::string& recipient,
        const std::string& message
    ) = 0;
};

class RegistrationService {
public:
    explicit RegistrationService(IEmailSender& email_sender)
        : email_sender_(email_sender) {}

    bool register_user(const std::string& email) {
        return email_sender_.send(
            email,
            "Hello"
        );
    }

private:
    IEmailSender& email_sender_;
};

class MockEmailSender : public IEmailSender {
public:
    MOCK_METHOD(
        bool,
        send,
        (const std::string& recipient, const std::string& message),
        (override)
    );
};

TEST(RegistrationServiceTest, SendsWelcomeEmailToRegisteredUser) {
    MockEmailSender email_sender;
    RegistrationService service{email_sender};

    EXPECT_CALL(
        email_sender,
        send(
            "xoore4ik@gmail.con",
            "Hello"
        )
    )
        .Times(1)
        .WillOnce(testing::Return(true));

    const bool result = service.register_user("xoore4ik@gmail.con");

    EXPECT_TRUE(result);
}
```

## Как ты контролируешь уровень покрытия кода тестами?

Я пишу на двух языках: `python` и `C++`

На python  есть библиотека `coverage`, которая интегрируется с `pytest` (палгин `pytest-cov`) и способна обрабатывать различные сценарии.

Контроль выстраивается автоматически на этапе сборки Pull Request. В репозитории фиксируется минимальный допустимый порог, например 80% для line и branch coverage; если он не достигнут, PR блокируется

На `C++` есть CLI-утилита `llvm-cov` от компилятора `Clang`, которая генерирует подробный отчет по результатам тестирования

Тестирование при помощи `llvm-cov` состоит из нескольких шагов:
1) Создание бинарного файла с тестами и опциями: 
* `-fprofile-instr-generate` - сбор профиля выполнения: какие участки кода были вызваны и сколько раз
* `-fcoverage-mapping` - связь счётчиков с участками исходного кода
2) Запустить тесты, указав файл профиля:
```bash
LLVM_PROFILE_FILE="<test>.profraw" ./<path_to_test>
```
`.profraw` содержит сырые счётчики выполнения функций, строк и ветвей
3) Индексация профиля
Файл `.profraw` является сырым представлением вызова всех функций и их счётчиков. Далее необходимо конвертировать эти данные в понятный `llvm-cov` файл `.profdata`.
```bash
llvm-profdata merge \
	-sparse \
	<path_to_.profraw> \
	-o <path_to_.profdata>
```
4) Генерация html
```bash
llvm-cov show \
	./<path_to_test> \
	-instr-profile=<path_to_.profdata>
	-format=html \
	-output-dir=coverage_html \
	-show-line-counts-or-regions \
	-show-branches=percent \
	src/ # Учитывать только исходники из директории src/, исключая код тестов и зависимости
```
5) Генерация данных для CI (например, SonarQube)
```bash
llvm-cov export ./<path_to_test> -format=lcov -instr-profile test.profdata > coverage.info
```
