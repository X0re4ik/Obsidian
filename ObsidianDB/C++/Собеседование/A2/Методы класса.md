
### Что такое конструктор?

Особый вид метода класса, который автоматически вызывается при создании объекта класса
Особенности конструктора:
* Название идентично названию класса
* Не имеет возвращаемого значения

### Существует ли виртуальный конструктор?

Нет! Виртуальных конструкторов быть не может.


### Какие виды конструкторов ты знаешь?

1) Конструктор по умолчанию
Можно вызвать без аргументов. Неявно объявляется, если нет пользовательских конструкторов или шаблонов конструкторов; может оказаться удалённым, если невозможно инициализировать базы или поля.

2) Консруктор с параметрами
Если мы хотим явно создавать объект из опредленных параметров, то используем этот вид контрукторов. Конструкторам с параметрами разрешены перегрузки, поэтому на них распостраняются все правила разрешения перегрузок

3) Конструктор копирования (Copy Constructor)
**Создание по умолчанию:** Если пользователь не объявил конструктор копирования, компилятор объявляет его неявно. Он копирует базы и поля согласно их типам: сырой указатель копируется как адрес, а объект класса - своим конструктором копирования. Неявный конструктор может оказаться удалённым.
**Описание:** Конструктор копирования производит копирование всех полей в новый объект
**Сигнатура:**
```C++
Foo(const Foo &foo);
```
**Примеры:**
Посмотрим на простую реализацию конструктора копирования:
```C++
class Foo {
private:
  int a_;

public:
  Foo(const Foo &foo) { a_ = foo.a_; }
};
```
Конструктор копирования принимает `const &` на объект того же типа и имеет доступ к приватным полям класса. Пример выше немного искусственный, так как нам бы подошла и стандартная реализация конструктора копирования

Рассмотрим более сложный вариант:
```C++
class Foo {
private:
  int *a_;

public:
  Foo(const Foo &foo) : a_(new int{*foo.a_}) {}
};
```
В примере выше (если опустить, что `_a` может принимать форму `nullptr`) мы вынуждены самим реализовывать конструктор копирования, иначе компилятор просто реализует за нас, что-то на подобии `Foo(const Foo &foo) : a_(foo.a_)`

4) Конструктор перемещения
5) Делегирующий конструктор

### Что такое оператор присваивания копированием? Чем он отличается от конструктора копирования?

Оператор присваивания копированием переносит состояние другого объекта в уже существующий объект. Конструктор копирования создаёт новый объект. Обычная сигнатура оператора: `T& operator=(const T&)`.

```cpp
struct Value {
    int x = 0;
    Value() = default;
    Value(const Value&) = default;
    Value& operator=(const Value&) = default;
};
Value a;
Value b = a; // Конструктор копирования
b = a;       // Оператор присваивания
```

Для класса с собственным ресурсом нужно корректно заменить старый ресурс и учесть самоприсваивание. Пример ручного управления ресурсом: [[Что такое конструктор копирования? Когда компилятор генерирует его неявно?#Разбор кейсов]].

### 8. Что такое виртуальная функция?

Виртуальная функция — это функция-член, которую предполагается переопределить в производных классах. Отличительная черта виртуальных функций — наличие ключевого слова `virtual`.

Чтобы наглядно рассмотреть роль `virtual`, рассмотрим следующий пример:

```cpp
#include <iostream>

class Base {
public:
  virtual void NameOf() { std::cout << "Base: NameOf" << std::endl; }
  void InvokingClass() { std::cout << "Base: InvokingClass" << std::endl; }
};

class Derived : public Base {
public:
  void NameOf() override { std::cout << "Derived: NameOf" << std::endl; }
  void InvokingClass() { std::cout << "Derived: InvokingClass" << std::endl; }
};

int main() {
  Derived aDerived;
  Base *pBase = &aDerived;
  pBase->InvokingClass(); // (2)
  pBase->NameOf();        // (3)
  return 0;
}
```

Пример выше выведет следующее значение:
```text
Base: InvokingClass
Derived: NameOf
```

Здесь наглядно продемонстрировано правило работы вызова виртуальных и невиртуальных функций:
* Вызов виртуальной функции разрешается в соответствии с динамическим (то есть фактическим) типом объекта, для которого она вызывается.
* Вызов невиртуальной функции разрешается в соответствии с типом указателя или ссылки (статическим типом).

Механизм виртуальных функций можно "подавить" при помощи явного указания базового класса и оператора разрешения видимости (`::`).
Например:

```cpp
int main() {
  Derived aDerived;
  Derived *pDerived = &aDerived;
  pDerived->Base::NameOf();
  return 0;
}
```

Начиная с C++11 появилось ключевое слово `override`, которое позволяет явно сказать компилятору, что эта функция переопределяет виртуальную функцию родителя. Это позволяет нам избавиться от ошибок, когда вместо переопределения мы случайно создали новый метод с чуть иными параметрами.

```cpp
class Base {
public:
  virtual void NameOf() { std::cout << "Base: NameOf" << std::endl; }
};

class Derived : public Base {
public:
  void NameOf() override { std::cout << "Derived: NameOf" << std::endl; }
};
```

У виртуальных функций есть еще одна возможность: они способны превращать классы в абстрактные. Если хотя бы 1 виртуальная функция объявлена как **чистая виртуальная функция** (при помощи `= 0`), то весь класс является абстрактным. Создать экземпляр (объект) абстрактного класса невозможно.

```cpp
class Base { // Абстрактный класс
public:
  virtual void NameOf() = 0; // Чистая виртуальная функция
};
```

### 9. Что такое vtable?

В C++ динамическое связывание (полиморфизм) обычно реализовано при помощи виртуальной таблицы (**vtable**). Это распространённая реализация, а не требование стандарта.

**vtable** — таблица адресов виртуальных функций и служебных данных, которую создаёт компилятор для полиморфного класса. Она общая для объектов соответствующего типа; при множественном наследовании таблиц может быть несколько. Конкретное размещение зависит от ABI.

Для того чтобы объекты знали, к какой таблице обращаться, компилятор неявно добавляет внутрь каждого объекта полиморфного класса специальный указатель на эту таблицу — **vpointer (vptr)**. Это можно легко заметить, сравнив размеры объектов классов с виртуальными методами и без них.

```cpp
#include <iostream>

class Base {
public:
  virtual void NameOf() {}
};

class NotVirtualBase {
public:
  void NameOf() {}
};

int main() {
  std::cout << "Base: " << sizeof(Base) 
            << "\nNotVirtualBase: " << sizeof(NotVirtualBase) << std::endl;
  return 0;
}
```

**Вывод (на x64 архитектуре):**
```text
Base: 8
NotVirtualBase: 1
```

Базовый класс содержит те самые 8 байт, которые весит указатель (`vptr`) на 64-битной машине. Пустой класс `NotVirtualBase` весит 1 байт (минимально возможный размер объекта в C++ для обеспечения уникальности адресов).

#### Множественное наследование
При множественном наследовании объект может содержать несколько указателей `vptr` для полиморфных базовых подобъектов. Производный класс может разделять `vptr` с одной из баз. Число указателей и устройство таблиц зависят от иерархии и ABI.

Рассмотрим процесс выделения памяти и вызовов на примере множественного наследования:

```cpp
class Base1 {
public:
  virtual void base_1() {}
  virtual void f() {}
};

class Base2 {
public:
  virtual void base_2() {}
  virtual void f() {}
};

class Children : public Base1, public Base2 {
public:
  int x;
};

int main() {
  Children* c = new Children();
  
  c->base_1(); // (1)
  c->base_2(); // (2)

  Base2* b2 = static_cast<Base2*>(c); // (3)
  b2->base_2(); // (4)

  // c->f(); // (5) - Ошибка компиляции
  
  return 0;
}
```

Разберем, что происходит в каждом из отмеченных случаев:

1. `c->base_1();` — Компилятор знает, что подобъект `Base1` находится в начале объекта `Children` (со смещением 0). Происходит обращение к первой vtable и вызов `base_1`. Здесь всё просто.
2. `c->base_2();` — Компилятор знает, что подобъект `Base2` располагается со смещением (обычно 8 байт, сразу после `Base1`). Компилятор неявно корректирует (сдвигает) указатель `this`, чтобы передать в метод `base_2` правильный адрес.
3. `Base2* b2 = static_cast<Base2*>(c);` — Здесь происходит явное приведение типов (upcast). Физически сам объект в памяти не меняется, но **численное значение указателя `b2` сдвигается** (увеличивается на размер `Base1`), чтобы `b2` указывал строго на начало подобъекта `Base2` внутри `Children`. Это называется *pointer adjustment*.
4. `b2->base_2();` — Вызываем метод через указатель на `Base2`. Так как `b2` уже указывает на правильное смещение, метод отрабатывает корректно.
5. `c->f();` — **Ошибка компиляции (ambiguous call)**. Оба родительских класса имеют виртуальный метод `f()`. C++ не знает, какую реализацию выбрать по умолчанию. Эту проблему (неоднозначность) можно решить двумя способами: либо явно указать класс (`c->Base1::f();`), либо переопределить метод `f()` внутри класса `Children`.

### Зачем используется ключевое слово `virtual`?

Ключевое слово `virtual` объявляет виртуальный метод: при вызове через указатель или ссылку на базовый класс выбирается реализация по фактическому типу объекта. Также применяется для виртуального наследования.

### Зачем используется ключевое слово `final`?

Ключевое слово `final` указывает, что виртуальная функция не может быть переопределена в производном классе или что класс не может наследоваться.

**Пример с виртуальной функцией**

```C++
class Base1 {
public:
  virtual void base_1() {}
};

class Children1 : public Base1 {
public:
  void base_1() override final {}
};

class Children2 : public Children1 {
public:
  void base_1() override {
  } // Ошибка, так как в Children1 метод base_1 помечен как final
};
```

**Пример с классом**

```C++
class Base1 {
public:
  virtual void base_1() {}
};

class Children1 final : public Base1 {
public:
  void base_1() override {}
};

class Children2 : public Children1 {
}; // Ошибка компиляции, Children1 помечен как final, дальнейшее наследование
   // невозможно
```

### Зачем используется ключевое слово `override`?

Начиная с C++11 появилось ключевое слово `override`, которое позволяет явно сказать компилятору, что эта функция переопределяет виртуальную функцию родителя. Это позволяет нам избавиться от ошибок, когда вместо переопределения мы случайно создали новый метод с чуть иными параметрами.

Если подходящего виртуального метода базы нет, компилятор выдаст ошибку. Пример приведён в [[Методы класса#8. Что такое виртуальная функция?]].

### Что такое чистая виртуальная функция?

Чистая виртуальная функция - виртуальный метод, объявленный с `= 0`. Пока в классе остаётся такая функция без переопределения, класс абстрактный. У чистой виртуальной функции может быть реализация вне класса; это не отменяет её чистоту.

**Пример:**
```C++
class Base1 {
public:
  // Чисто виртуальная функция
  virtual void base_1() = 0;
};
```


### Как получить ошибку `pure virtual call`?

Виртуальный вызов чистой виртуальной функции из конструктора или деструктора того же объекта приводит к неопределённому поведению (UB). В типичных реализациях косвенный вызов заканчивается диагностикой `pure virtual call`, но стандарт не гарантирует именно её.

**Например**
```C++
class Base {
public:
  Base() { reallyDoIt(); }
  void reallyDoIt() { doIt(); } // DON'T DO THIS
  virtual void doIt() = 0;
};

class Derived : public Base {
  void doIt() {}
};

int main(void) {
  Derived d; // UB; типичная диагностика: pure virtual function call
}
```

При выполнении конструктора `Base` виртуальные вызовы не переходят к переопределениям `Derived`. Цепочка `reallyDoIt -> doIt` пытается виртуально вызвать чистую функцию `Base::doIt`. Это UB; `pure virtual call` - типичная диагностика среды выполнения.

Стоит отметить, что компилятор откровенные "ляпы" умеет отлавливать.

**Например**
```C++
class Base {
public:
  Base() { doIt(); }
  virtual void doIt() = 0;
};
```
```bash
>> g++ main.cpp -o main
main.cpp: In constructor ‘Base::Base()’:
main.cpp:5:16: warning: pure virtual ‘virtual void Base::doIt()’ called from constructor
    5 |   Base() { doIt(); }
      |            ~~~~^~
/usr/bin/ld: /tmp/cc2ZQJys.o: в функции «Base::Base()»:
main.cpp:(.text._ZN4BaseC2Ev[_ZN4BaseC5Ev]+0x26): неопределённая ссылка на «Base::doIt()»
collect2: error: ld returned 1 exit status
```

Если вызов спрятан под обычным методом, программа часто компилируется, но виртуальный вызов всё равно приводит к UB; конкретная диагностика не гарантируется.

Рассмотрим аналогичный пример в деструкторе

**Пример**
```C++
class Base {
public:
  void reallyDoIt() { doIt(); }
  virtual void doIt() = 0;
  virtual ~Base() {
    std::cout << "~Base()" << std::endl;
    reallyDoIt(); // (1)
  }
};

class Derived : public Base {
public:
  void doIt() {}
  ~Derived() { std::cout << "~Derived()" << std::endl; }
};
```

Ситуация аналогичная с конструктором только в противоположном смысле. В момент времени, когда вызывается `(1)` - объект `Derived` уже уничтожен и его переопредленный момент `doIt` не виден, как результат - `pure virtual call`.

### Что такое деструктор?

Деструктор — это специальный метод класса, который вызывается автоматически при уничтожении объекта. Его главная цель — деинициализация объекта, то есть освобождение ресурсов (динамической памяти, сетевых сокетов, файловых дескрипторов, мьютексов и т.д.), которые были захвачены за время жизни объекта. 

Именно на деструкторах строится фундаментальная идиома C++ под названием **RAII (Resource Acquisition Is Initialization)**. Без автоматического и гарантированного освобождения ресурсов в деструкторах концепция RAII была бы невозможна.

#### Порядок разрушения объекта
Разрушение объекта происходит строго в порядке, обратном его конструированию:
1. Выполняется тело деструктора самого класса.
2. Вызываются деструкторы полей (объектов-членов) класса в порядке, строго обратном их объявлению в классе.
3. Вызываются деструкторы базовых классов (в случае множественного наследования — в порядке, обратном их перечислению в списке наследования).

*Примечание: Если класс предполагается использовать полиморфно (т.е. удалять объекты дочерних классов через указатель на базовый класс), деструктор базового класса обязательно должен быть объявлен как `virtual`.*

#### Исключения в деструкторе и `noexcept`
Начиная с C++11, все деструкторы по умолчанию неявно помечены спецификатором `noexcept` (точнее `noexcept(true)`), если только программист явно не укажет `noexcept(false)` или если базовый класс/поля не имеют потенциально бросающих деструкторов.

Такое строгое ограничение связано с механизмом обработки исключений и процессом **раскрутки стека (stack unwinding)**.
Когда в программе выбрасывается исключение, C++ начинает разматывать стек вызовов в поисках подходящего блока `catch`. В процессе этой раскрутки для всех локальных объектов автоматически вызываются деструкторы. Если в этот момент один из деструкторов попытается выбросить **второе (новое) исключение**, возникнет ситуация двух одновременно активных исключений. Механизм обработки C++ не может с этим справиться, поэтому программа немедленно аварийно завершается вызовом функции `std::terminate`.

**Пример аварийного завершения:**
```cpp
#include <iostream>
#include <stdexcept>

class Base {
public:
  ~Base() {
    std::cout << "~Base()" << std::endl;
    // Деструктор по умолчанию noexcept. Выброс исключения приведет к std::terminate
    throw std::runtime_error("Error inside destructor"); 
  }
};

int main() {
  try {
    Base b; // При выходе из блока try вызовется деструктор
  } catch (const std::runtime_error& e) {
    std::cout << e.what() << std::endl;
  }
  return 0;
}
```

**Вывод программы:**
```text
~Base()
terminate called after throwing an instance of 'std::runtime_error'
  what():  Error inside destructor
Аварийный останов (core dumped)
```

### Зачем нужен виртуальный деструктор?

Виртуальный деструктор необходим для того, чтобы при удалении объекта производного класса через указатель на базовый класс гарантированно вызывался деструктор наследника (а за ним и базового класса). 

Удаление объекта производного класса через указатель на базовый без виртуального деструктора ведет к **неопределенному поведению (Undefined Behavior, UB)**. На практике это чаще всего выражается в том, что деструктор наследника просто не вызывается, что приводит к утечке ресурсов.

#### Пример необходимости виртуального деструктора:
```cpp
#include <iostream>

class Base {
public:
  Base() { std::cout << "Base()" << std::endl; }
  // Убери virtual, и ~Children() не будет вызван (возникнет UB)
  virtual ~Base() { std::cout << "~Base()" << std::endl; } 
};

class Children : public Base {
public:
  Children() : Base() { std::cout << "Children()" << std::endl; }
  
  // В современном C++ хорошим тоном является использование override для деструктора наследника
  ~Children() override { std::cout << "~Children()" << std::endl; } 
};

int main() {
  Base* base = new Children();
  delete base; // Вызывает ~Children(), затем ~Base()
  return 0;
}
```

#### Золотое правило проектирования классов:
Если класс **полиморфный** (то есть спроектирован для наследования и имеет хотя бы одну виртуальную функцию), его деструктор должен быть:
1. Либо **открытым и виртуальным** (`public virtual`).
2. Либо **защищенным и невиртуальным** (`protected non-virtual`).

Второй вариант (защищенный невиртуальный деструктор) используется, когда мы хотим разрешить наследование, но на уровне компиляции **запретить** удаление объекта через указатель на базовый класс.

#### Пример с защищенным деструктором:
```cpp
#include <iostream>
#include <memory>

class Base {
public:
    virtual void foo() { }
protected:
    ~Base() { std::cout << "~Base()\n"; } // Не виртуальный, но защищенный
};

class Derived : public Base {
public:
    ~Derived() { std::cout << "~Derived()\n"; }
};

int main() {
    Base* ptr = new Derived();
    // delete ptr; // ❌ Ошибка компиляции: деструктор Base недоступен извне

    // Правильный способ удаления (если мы точно знаем тип):
    delete static_cast<Derived*>(ptr); 

    // Или использование умных указателей (std::shared_ptr):
    std::shared_ptr<Base> sp = std::make_shared<Derived>(); 
    
    return 0;
}
```

**Продвинутый нюанс (почему работает `shared_ptr`):** 
В последнем примере при разрушении `sp` корректно вызовется деструктор `~Derived()`, несмотря на то, что у `Base` деструктор не виртуальный. Это происходит благодаря механизму **стирания типов (type erasure)**. Функция `std::make_shared<Derived>()` при создании запоминает реальный тип объекта в своем внутреннем управляющем блоке (control block) вместе с кастомным удалителем (deleter). 
*(Важно: с `std::unique_ptr<Base>` такой трюк без написания собственного deleter'а не пройдет — он потребует виртуального деструктора).*


### В чем особенность константных методов класса?

Методы, помеченные спецификатором `const`, не позволяют изменять обычные поля через `this` и вызывать через него неконстантные методы. Их можно вызывать для константных объектов. Сохранение логического состояния - обязанность автора: `mutable` и данные по указателям всё ещё могут изменяться.

Если заглянуть "под капот", то особенность константных методов заключается в типе неявно передаваемого указателя `this`:
* В обычном методе выражение `this` имеет тип `T*`.
* В `const` методе - `const T*`. Самому `this` нельзя присвоить новый адрес: это выражение, а не изменяемая переменная.

#### Побитовая и логическая константность
С точки зрения компилятора, `const` ограничивает изменение обычных полей через константный доступ; поля `mutable` составляют исключение. Однако в архитектуре часто используется **логическая константность (logical constness)** — когда видимое состояние объекта не меняется, но внутри (под капотом) происходят изменения (например, кэширование, подсчет ссылок, захват мьютекса). 

Чтобы обойти побитовую константность, в C++ есть два способа:
1. **Ключевое слово `mutable`:** Позволяет изменять конкретное поле даже внутри `const` метода.
   ```cpp
   struct Point {
     mutable int cached_hash;
     int x, y, z;
   
     int getHash() const { 
       // Можно изменять, несмотря на то, что метод const
       cached_hash = x + y + z; 
       return cached_hash; 
     }
   };
   ```
2. **Изменение данных по указателю:** Сам указатель изменить нельзя (он часть объекта и подчиняется правилу `const T* const`), но данные, на которые он указывает (лежащие в куче), изменять можно.
   ```cpp
   struct Point {
     int* x = new int{1};
     
     void modifyData() const {
       *x = 42; // ОК: данные по адресу меняются, сам указатель x - нет
     }
   };
   ```

#### Const и потокобезопасность
`const` сам по себе не обеспечивает потокобезопасность пользовательского класса. Для стандартной библиотеки действуют отдельные требования к отсутствию гонок данных. Если константный метод изменяет общий кэш или счётчик через `mutable`, при параллельных вызовах нужна синхронизация, например `std::atomic` или `mutable std::mutex`.

#### Перегрузка по константности
Методы класса можно перегружать исключительно по наличию спецификатора `const`. Это широко используется в STL (например, в `std::vector` или `std::string`), чтобы возвращать разные типы ссылок в зависимости от того, с каким объектом мы работаем:
```cpp
class MyArray {
    int data[10];
public:
    // Для неконстантных объектов (разрешает чтение и запись)
    int& operator[](size_t i) { return data[i]; }
    
    // Для константных объектов (разрешает только чтение)
    const int& operator[](size_t i) const { return data[i]; }
};
```


### Правило 3, Правило 5 и Правило 0

#### Правило 3
Историческое правило (до стандарта C++11): если ваш класс владеет ресурсами, требующими ручного управления (например, сырыми указателями, файловыми дескрипторами), и вы явно определяете **хотя бы один** из следующих трех методов, то нужно продумать поведение всех трёх (реализовать, использовать `= default` или запретить через `= delete`):
1. Деструктор
2. Конструктор копирования
3. Оператор присваивания копированием

*Почему?* Потому что сгенерированные компилятором копирующие методы делают "поверхностное копирование" (побитовое копирование указателей). При разрушении оригинала и копии это приведет к двойному освобождению одного и того же ресурса (double free).

#### Правило 5
С появлением в C++11 семантики перемещения (move semantics) Правило 3 расширилось. Если класс управляет ресурсами вручную, нужно продумать **пять** специальных функций, включая возможность запрета операций:
1. Деструктор
2. Конструктор копирования
3. Оператор присваивания копированием
4. Конструктор перемещения
5. Оператор присваивания перемещением

**Важный нюанс (Откат к копированию из-за деструктора):**
В C++ генерация специальных методов работает *на уровне конкретного класса*. Если вы явно объявляете деструктор в классе (даже пустой: `~MyClass() {}` или `~MyClass() = default;`), компилятор **отключает автоматическую генерацию** методов перемещения *именно для этого класса*. 

При инициализации из `std::move(obj)` возможен *тихий откат к копированию*, если доступен подходящий конструктор копирования. Иначе код не скомпилируется. Копирование вместо перемещения может привести к просадкам производительности (например, будет скопирован весь `std::vector`).

Если после объявления деструктора классу нужны операции перемещения и копирования, их можно явно объявить, следуя Правилу 5:
```cpp
class Widget {
public:
    virtual ~Widget() = default; // Убило неявное перемещение
    
    // Явно возвращаем перемещение
    Widget(Widget&&) = default;
    Widget& operator=(Widget&&) = default;
    
    // Явно возвращаем копирование (так как оно тоже может отключиться)
    Widget(const Widget&) = default;
    Widget& operator=(const Widget&) = default;
};
```
*(Примечание: если класс-наследник не объявляет свой деструктор явно, он сохраняет неявно сгенерированные методы перемещения для своих полей, даже если наследуется от базы с виртуальным деструктором).*

#### Правило 0
Современный стандарт проектирования в C++ (идиома RAII): класс **вообще не должен** содержать пользовательских деструкторов, конструкторов копирования/перемещения или операторов присваивания. 

Вместо ручного управления ресурсами класс должен делегировать эти обязанности стандартным контейнерам (`std::vector`, `std::string`) и умным указателям (`std::unique_ptr`, `std::shared_ptr`). Они сами знают, как правильно копироваться, перемещаться и удаляться. Доступность копирования и перемещения определяется полями и базами: например, поле `std::unique_ptr` запрещает неявное копирование, но допускает перемещение.


### Использование `static` для полей и методов класса в C++

#### 1. `static` для полей класса

В современном C++ объявить и инициализировать статические поля класса можно несколькими способами:

1. **Через оператор разрешения имени `::`** (только объявление в теле класса, определение выносится вне класса, обычно в `.cpp` файл).
2. **С помощью `inline` (С++17)** — позволяет инициализировать поля любых типов прямо в теле класса без нарушения правила одного определения (ODR).
3. **С помощью `const` (С++98)** — внутриклассовая инициализация разрешена **только для целочисленных типов (integral) и перечислений (enum)**. Инициализировать таким образом `float`, `std::string` или другие типы внутри класса нельзя.
4. **С помощью `constexpr` (С++11)** — для литеральных типов (включая `float`). Начиная с С++17 такие поля неявно становятся `inline`.

```cpp
#include <iostream>
#include <string>

struct A {
  static int a;                  // 1. Только объявление
  inline static int b = 10;      // 2. С++17, любой тип
  inline static std::string s = "text"; // 2. С++17
  static const int c = 100;      // 3. C++98, только целочисленные/enum
  static constexpr float d = 3.14f; // 4. С++11 (С++17 неявный inline)
};

int A::a = 1; // Определение для a (выделение памяти)

int main() {
  // Обращение к статическим полям
  std::cout << A::a << "\n"; // Через оператор разрешения имен (::)
  
  auto obj = A();
  std::cout << obj.a << "\n"; // Через экземпляр объекта (obj. или obj->)
  return 0;
}
```

#### 2. `static` для методов класса

Ситуация с методами аналогична: вызывать их можно через оператор разрешения имен (`::`) или через экземпляр объекта.
Внутри статического метода **нет неявного указателя `this`**, поэтому на них наложено несколько ограничений:
* Невозможность обращения к нестатическим полям и методам класса напрямую (только если передать объект в качестве аргумента).
* Невозможность динамического переопределения (полиморфизм), так как методы не могут быть `virtual`.
* Невозможность навесить cv-квалификаторы (`const`, `volatile`) или ref-квалификаторы на сам метод.

Отметим, что статические методы **наследуются**. То есть, если класс `A` наследует `B`, то публичный метод `B::foo()` будет доступен и как `A::foo()`.

### 3. Хранение `static` переменных и жизненный цикл

Статические переменные существуют в единственном экземпляре для всех объектов данного класса. 

**Распределение по сегментам памяти:**
* Неинициализированные (или инициализированные нулем) статические переменные хранятся в секции **`.bss`**.
* Инициализированные ненулевым значением (неконстантные) — в секции **`.data`**.
* Константные инициализированные переменные — в секции **`.rodata`**.

**Жизненный цикл:** начинается до входа в `main` (на этапе статической или динамической инициализации) и заканчивается при завершении работы программы.

#### 4. Проблема порядка статической инициализации (Static Initialization Order Fiasco)

Поскольку статические переменные инициализируются до вызова `main`, возникает проблема: стандарт C++ **не гарантирует** порядок инициализации статических объектов, находящихся в разных единицах трансляции (`.cpp` файлах). Если одна статическая переменная при инициализации зависит от другой из другого файла, программа может упасть из-за обращения к неинициализированной памяти.

**Решение:** использование идиомы «Синглтон Майерса» (Meyers Singleton), где статическая переменная объявляется локально внутри функции:

```cpp
MyClass& getInstance() {
    static MyClass instance; // Инициализируется лениво при первом вызове функции
    return instance;
}
```
*Примечание:* Начиная с C++11, инициализация локальных статических переменных гарантированно является **потокобезопасной** (Magic Statics).

#### 5. Шаблоны и `static`

При инстанцировании шаблонного класса для каждого нового типа генерируется **свой собственный независимый экземпляр** статического поля и метода.

```cpp
template <typename T> 
class A {
public:
  A() { count_++; }
  inline static int count_ = 0;
};

int main() {
  auto a = A<int>();
  auto b = A<float>();
  auto c = A<int>();

  // Выведет: 2 - 1 - 2
  // A<int> и A<float> имеют совершенно независимые переменные count_
  std::cout << c.count_ << " - " << b.count_ << " - " << c.count_ << "\n";
  return 0;
}
```

#### 6. Многопоточность (бонус)

Если статическое поле пометить ключевым словом `thread_local`, то экземпляр этой переменной будет **своим для каждого потока выполнения**, а не один на весь процесс (хранение будет осуществляться в сегментах `.tbss` / `.tdata`).



### Использование `inline` для полей и методов класса

`inline` позволяет размещать определения в заголовке, включаемом в несколько единиц трансляции, при соблюдении ODR. Это не гарантия подстановки тела функции вместо вызова.

Метод, определённый внутри класса, неявно `inline` (в обычном заголовке, вне именованного модуля). Определение метода вне класса в заголовке можно явно пометить `inline`.

С C++17 `inline static` поле можно определить и инициализировать прямо в классе; это одно общее поле, а не отдельное для каждого `.cpp`. К нестатическим полям `inline` неприменим.

```cpp
struct Counter {
    inline static int count = 0;
    int get() const { return count; }
    void increment();
};
inline void Counter::increment() { ++count; }
```

### Зачем используется ключевое слово `mutable`?

Для поля класса `mutable` разрешает изменение даже у константного объекта или внутри `const` метода. Для лямбды делает `operator()` неконстантным, позволяя менять захваченные по значению копии. Исходная переменная при этом не меняется.

```cpp
int x = 10;
auto next = [x]() mutable { return ++x; };
next(); // 11; внешний x по-прежнему 10
```

Изменение данных константного объекта
```C++
struct A {
  mutable int x = 10;
};

int main() {
  const A a;
  a.x = 20;

  std::cout << "a.x=" << a.x << std::endl; // a.x=20
  return 0;
}
```



## Что такое object slicing (срезка типа)? Приведи пример, когда это происходит.

**Object slicing** - это ситуация, когда объект производного класса копируют в объект базового класса по значению, поэтому сохраняется только базовая часть объекта, а данные и поведение, специфичные для потомка, теряются
**Пример**
```C++
class Animal {
public:
    virtual void speak() const {
        std::cout << "Animal\n";
    }
};

class Dog : public Animal {
public:
    void speak() const override {
        std::cout << "Dog\n";
    }
};

Dog dog;
Animal animal = dog;
animal.speak();
dog.speak();
```
