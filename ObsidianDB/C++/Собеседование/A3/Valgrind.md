# Valgrind: конспект по Memcheck

Этот конспект собран по итогам разбора Valgrind и Memcheck: от принципа работы до диагностики утечек и запуска в CI.

## 1. Что такое Valgrind

**Valgrind** — среда динамического анализа Linux-программ. Она запускает клиентскую программу не напрямую, а через контролируемую среду исполнения.

Упрощённая схема:

```text
Обычный запуск:
app → CPU

Запуск под Valgrind:
app → Valgrind → CPU
```

Valgrind не является обычным логгером и не просто наблюдает за процессом. Он динамически преобразует исполняемый машинный код программы, добавляет проверки выбранного инструмента и исполняет инструментированную версию на настоящем CPU.

## 2. Dynamic Binary Instrumentation

Valgrind работает с уже скомпилированным ELF-бинарником и подключаемыми библиотеками.

При первом попадании в участок машинного кода Valgrind:

1. Читает машинные инструкции исходной программы.
2. Переводит их во внутреннее представление.
3. Добавляет проверки выбранного инструмента, например Memcheck.
4. Генерирует инструментированный машинный код.
5. Сохраняет результат в `translation cache`.
6. Исполняет этот код на реальном CPU.

Упрощённо:

```text
Машинный код программы
        ↓
Внутреннее представление Valgrind (IR)
        ↓
Добавление проверок Memcheck
        ↓
Инструментированный машинный код
        ↓
CPU
```

### Basic block и translation cache

Valgrind обычно не переводит весь ELF при старте. Он обрабатывает только те **basic blocks**, до которых выполнение реально дошло.

**Basic block** — последовательность машинных инструкций с одним входом и без переходов в середине. Обычно блок заканчивается на условном переходе, `call`, `return` или безусловном переходе.

```text
Первый вход в блок:
исходный блок → трансляция → проверки → translation cache → исполнение

Повторный вход:
translation cache → исполнение
```

`translation cache` не отменяет проверки Memcheck: он лишь предотвращает повторную трансляцию одного и того же блока. Проверки в уже подготовленном блоке всё равно выполняются при каждом входе.

### Ограничение динамического анализа

Valgrind проверяет только реально выполненный путь программы.

```cpp
int* p = new int[2];

if (flag) {
    p[2] = 10;  // Ошибка выхода за границы.
}

delete[] p;
```

Если в запуске `flag == false`, блок с ошибкой не будет выполнен, инструментирован и проверен. Отсутствие ошибки в одном запуске не доказывает отсутствие дефекта в программе.

## 3. Почему Valgrind медленнее

Valgrind заметно медленнее нативного запуска по нескольким причинам:

- при первом входе в блок происходит JIT-подобная трансляция;
- к операциям с памятью добавляются проверки;
- Memcheck ведёт дополнительную теневую память с метаданными;
- требуется обновлять служебное состояние и формировать диагностику при ошибках.

Например, исходная операция по смыслу:

```text
записать 4 байта по адресу из регистра RAX
```

в Memcheck логически становится:

```text
1. Проверить, доступны ли 4 байта по адресу RAX.
2. Сообщить об ошибке, если адрес недоступен.
3. Выполнить исходную запись.
4. Отметить записанные байты как определённые.
```

`RAX` хранит адрес; запись выполняется в память по адресу `[RAX]`, а не в сам регистр.

## 4. Что делает Memcheck

**Memcheck** — инструмент Valgrind для поиска ошибок работы с памятью.

Он отслеживает:

- доступность адреса для чтения/записи;
- определённость значения: инициализированы ли биты данных;
- выделение и освобождение heap-памяти;
- соответствие пар выделения и освобождения;
- утечки памяти.

Главные вопросы Memcheck для операции доступа:

```text
1. Можно ли обратиться к этому диапазону адресов?
2. Определено ли используемое значение?
```

### Addressability и definedness

```cpp
int* p = new int[2];
p[0] = 42;
```

Состояние памяти:

| Элемент | Адрес доступен? | Значение определено? |
|---|---:|---:|
| `p[0]` | Да | Да |
| `p[1]` | Да | Нет |
| `p[2]` | Нет | Неважно |

```cpp
p[2] = 10;       // Invalid write: адрес за границей.
if (p[1] > 0) {} // Условие зависит от неинициализированного значения.
```

## 5. Основные сообщения Memcheck

### Invalid read / Invalid write

```text
Invalid read of size N
Invalid write of size N
```

Проблема в **адресе**: программа читает или пишет по недоступному адресу.

Типичные причины:

- выход за границы массива;
- use-after-free;
- обращение через `nullptr`;
- неправильный указатель;
- ошибка в арифметике указателей.

Пример:

```cpp
int* values = new int[2];
values[2] = 42;  // Invalid write of size 4 на типичной системе.
delete[] values;
```

`values[2]` — это `*(values + 2)`. Для массива из двух элементов допустимы только `values[0]` и `values[1]`.

### Как читать адресный контекст

```text
Address 0x... is 0 bytes after a block of size 8 alloc'd
```

Это означает: ошибочный адрес находится сразу после выделенного блока размером 8 байт.

На типичной системе `new int[2]` выделит:

```text
2 × sizeof(int) = 2 × 4 = 8 байт
```

Полезные варианты сообщений:

| Фраза | Значение |
|---|---|
| `0 bytes after a block of size N` | Доступ сразу за правой границей блока |
| `K bytes after a block of size N` | Доступ правее конца на K байт |
| `K bytes before a block of size N` | Доступ левее начала блока |
| `K bytes inside a block of size N free'd` | Доступ к уже освобождённому блоку |
| `Address 0x0 is not stack'd, malloc'd or (recently) free'd` | Вероятен `nullptr` или невалидный указатель |

Важно различать:

```text
Invalid write of size 4
```

— размер операции записи, и:

```text
4 bytes inside a block
```

— смещение ошибочного адреса от начала блока.

### Use-after-free

```cpp
int* data = new int[3];
delete[] data;
data[1] = 99;  // use-after-free
```

После `delete[]` блок становится недоступным. Сам указатель остаётся числом-адресом, но становится **висячим указателем** (*dangling pointer*).

Типичный лог:

```text
Invalid write of size 4
Address ... is 4 bytes inside a block of size 12 free'd
```

В отчёте обычно есть:

1. место неправильного доступа;
2. место освобождения блока;
3. место первоначального выделения.

### Mismatched allocation/deallocation

Пары должны совпадать:

| Выделение | Освобождение |
|---|---|
| `new T` | `delete p` |
| `new T[N]` | `delete[] p` |
| `malloc`, `calloc`, `realloc` | `free(p)` |

Нарушения:

```cpp
int* a = new int[3];
delete a;       // Неверно: нужно delete[] a.

int* b = new int(42);
delete[] b;     // Неверно: нужно delete b.

int* c = static_cast<int*>(std::malloc(3 * sizeof(int)));
delete[] c;     // Неверно: нужно std::free(c).
```

Memcheck обычно сообщает:

```text
Mismatched free() / delete / delete []
```

Это undefined behavior. Нельзя полагаться на конкретное внутреннее устройство аллокатора или на то, что код «случайно работает».

### Неинициализированные значения

```cpp
int x;
int y = x + 1;

if (y > 10) {
    // ...
}
```

`x` не инициализирован. Неопределённость распространяется в `y`.

Memcheck может не сообщить ошибку на простом копировании:

```cpp
int y = x;
```

Но он обычно ругается, когда неопределённое значение влияет на поведение программы:

```cpp
if (x == 0) {}  // Выбор ветки.
p[x] = 42;      // Вычисление адреса.
std::cout << x; // Форматирование и вывод значения.
```

Типичное сообщение:

```text
Conditional jump or move depends on uninitialised value(s)
```

Другой вариант:

```text
Use of uninitialised value of size N
```

### Неинициализированный буфер и syscall

```cpp
char buffer[16];
buffer[0] = 'H';
buffer[1] = 'i';
buffer[2] = '
';

write(STDOUT_FILENO, buffer, 16);
```

Адрес `buffer` корректен, но инициализированы лишь первые 3 байта. В `write` передаются все 16 байт.

Типичный отчёт:

```text
Syscall param write(buf) points to uninitialised byte(s)
```

Исправление:

```cpp
write(STDOUT_FILENO, buffer, 3);
```

либо инициализация всего буфера:

```cpp
char buffer[16] = {};
```

## 6. Как читать стек Valgrind

Пример:

```text
Invalid write of size 4
    at process_data(User*) (processor.cpp:42)
    by main (main.cpp:17)
```

Читай сверху вниз:

```text
Ошибка проявилась в process_data() на processor.cpp:42.
process_data() был вызван из main() на main.cpp:17.
```

Если в стеке есть стандартная библиотека:

```text
Invalid read of size 4
    at std::vector<int>::operator[](unsigned long) (...)
    by process_data() (app.cpp:42)
    by main (app.cpp:90)
```

Начинай расследование с первого фрейма **своего кода**:

```text
process_data() (app.cpp:42)
```

Часто STL корректна, а в неё передали неверный индекс, объект с истёкшим временем жизни или уже повреждённые данные.

## 7. Debug information: `-g` и оптимизации

Для понятных отчётов собирай программу с debug information:

```bash
g++ -std=c++20 -g -Og -Wall -Wextra -Wpedantic main.cpp -o app
```

### Что делает `-g`

`-g` добавляет в ELF отладочную информацию, обычно DWARF:

```text
адрес машинной инструкции
→ функция
→ исходный файл
→ номер строки
```

`-g` не меняет логику программы и не включает отладчик. Он добавляет данные, которые потом читают Valgrind, GDB, IDE и другие инструменты.

Без `-g`:

```text
at 0x1091B2: ???
by 0x1091D0: ???
```

С `-g`:

```text
at process_data() (processor.cpp:42)
by main (main.cpp:17)
```

### Что делает `-Og`

`-Og` — уровень оптимизации, ориентированный на удобство отладки.

```text
-g  → как сопоставить машинный адрес с исходным кодом
-Og → насколько сильно компилятор перестраивает исходный код
```

При `-O3` компилятор может inline-ить функции, удалять локальные переменные, переставлять и объединять инструкции, разворачивать циклы и удалять код. Поэтому даже с `-g` стек и строки могут хуже соответствовать исходнику.

Практический порядок при сложном баге:

```bash
# Близко к release, но с символами
g++ -g -O2 main.cpp -o app

# Удобнее для диагностики
g++ -g -Og main.cpp -o app

# Максимально простой учебный / repro-вариант
g++ -g -O0 main.cpp -o app
```

После исправления полезно повторить проверку в оптимизированной сборке: undefined behavior может по-разному проявляться при `-O2` и `-O3`.

### Debug symbols библиотек

`-g` у твоего приложения добавляет debug information только в твой ELF, а не в `libc.so`, `libstdc++.so` и другие уже установленные библиотеки.

Для подробностей внутри библиотек нужны их отдельные debug-symbol packages или отдельные debug-файлы. Если debug info лежит в нестандартном месте, можно задать путь:

```bash
valgrind --extra-debuginfo-path=/path/to/debug/files ./app
```

## 8. Утечки памяти

В конце работы Memcheck может проверить, какие heap-блоки были выделены, но не освобождены.

Для подробностей:

```bash
valgrind   --tool=memcheck   --leak-check=full   --show-leak-kinds=all   ./app
```

Memcheck классифицирует утечки по достижимости блока от живых корней: стека, глобальных переменных, регистров и известных областей памяти.

### Категории утечек

| Категория | Значение | Приоритет |
|---|---|---|
| `definitely lost` | Указатель на начало блока полностью потерян | Исправлять обязательно |
| `indirectly lost` | Блок доступен только через другой уже потерянный блок | Исправлять корневую утечку |
| `possibly lost` | Остался подозрительный указатель внутрь блока | Расследовать |
| `still reachable` | Блок не освобождён, но достижим по корректному указателю на начало | Оценить контекст |
| `suppressed` | Ошибка/утечка скрыта suppression-правилом | Проверить правило |

### Definitely lost

```cpp
int* p = new int[10];
p = nullptr;
```

Последний указатель на начало блока потерян. Корректно вызвать `delete[]` уже невозможно.

### Indirectly lost

```cpp
struct Node {
    Node* next;
    int value;
};

Node* first = new Node{nullptr, 1};
first->next = new Node{nullptr, 2};
first = nullptr;
```

```text
Node 1 → definitely lost
Node 2 → indirectly lost
```

Второй узел был доступен только через первый, но первый потерян.

### Possibly lost

```cpp
int* array = new int[10];
int* middle = array + 3;
array = nullptr;
```

`middle` указывает внутрь блока, но не на его начало. Через `middle` нельзя делать:

```cpp
delete[] middle;  // Undefined behavior.
```

### Still reachable

```cpp
int* cache = nullptr;

int main() {
    cache = new int[100];
}
```

К завершению процесса глобальная `cache` всё ещё ведёт на начало блока. Его можно было бы освободить через `delete[] cache`.

`still reachable` не всегда баг: небольшой глобальный кэш в короткой CLI-утилите иногда допустим. Но это может стать проблемой в долгоживущем сервисе, если память растёт между запросами или рабочими циклами.

Очистка памяти ОС при завершении процесса не является критерием Memcheck: ОС освободит память и при `definitely lost`. Категория зависит от того, может ли программа найти и корректно освободить блок до завершения.

## 9. Полезные опции Memcheck

### Базовый подробный запуск

```bash
valgrind   --tool=memcheck   --leak-check=full   --show-leak-kinds=all   --track-origins=yes   ./app
```

| Опция | Назначение |
|---|---|
| `--tool=memcheck` | Выбрать Memcheck |
| `--leak-check=full` | Показать подробности утечек |
| `--show-leak-kinds=all` | Вывести все категории утечек |
| `--track-origins=yes` | Искать происхождение неинициализированных значений |
| `--log-file=...` | Перенаправить диагностику Valgrind в файл |
| `--error-exitcode=N` | Вернуть код N, если Memcheck нашёл ошибки |
| `--errors-for-leak-kinds=...` | Выбрать категории утечек, считающиеся ошибками |
| `--gen-suppressions=all` | Напечатать шаблоны suppression-правил |
| `--suppressions=file.supp` | Подключить suppression-файл |

### `--track-origins=yes`

Используй, когда видишь место опасного использования:

```text
Conditional jump or move depends on uninitialised value(s)
    at process() (processor.cpp:55)
```

но не понимаешь, откуда пришли неинициализированные байты.

Опция часто добавляет контекст:

```text
Uninitialised value was created by a stack allocation
    at parse_config() (config.cpp:18)
```

или:

```text
Uninitialised value was created by a heap allocation
    by load_values() (loader.cpp:27)
```

Она увеличивает накладные расходы, поэтому особенно полезна при расследовании конкретной ошибки.

### Логи и параллельные процессы

```bash
valgrind --log-file=valgrind.%p.log ./tests
```

`%p` заменяется на PID. Это важно для параллельных тестов: каждый процесс пишет в отдельный файл.

### CI и exit code

По умолчанию Valgrind может вернуть exit code самой программы. Поэтому тест может завершиться с `0`, хотя Memcheck нашёл ошибку.

Для CI:

```bash
valgrind   --tool=memcheck   --error-exitcode=42   ./tests
```

Если Memcheck найдёт ошибку, Valgrind вернёт `42` при успешном завершении клиентской программы. CI увидит ненулевой код и пометит job как failed.

### Политика утечек для CI

Показывать все категории, но падать только на реальные/подозрительные утечки:

```bash
valgrind   --tool=memcheck   --leak-check=full   --show-leak-kinds=all   --errors-for-leak-kinds=definite,indirect,possible   --error-exitcode=42   --log-file=valgrind.%p.log   ./tests
```

Так `still reachable` будет виден в логе, но сам по себе не сломает CI.

## 10. Suppression-файлы

Suppression-файл нужен для подавления конкретных известных сообщений, которые относятся к внешней библиотеке или сознательно принимаемому поведению и не могут быть исправлены в коде проекта.

Сгенерировать заготовки:

```bash
valgrind --gen-suppressions=all ./app
```

Подключить файл:

```bash
valgrind --suppressions=valgrind.supp ./app
```

Пример правила:

```text
{
   known_external_library_conditional
   Memcheck:Cond
   fun:external_library_internal
   fun:external_library_api
}
```

Правило должно быть узким: конкретный тип ошибки и конкретный стек. Нельзя использовать suppression как способ скрыть все ошибки и сделать CI зелёным.

## 11. Рекомендуемые команды

### Учебный запуск

```bash
g++ -std=c++20 -g -Og -Wall -Wextra -Wpedantic main.cpp -o app

valgrind   --tool=memcheck   --leak-check=full   --show-leak-kinds=all   --track-origins=yes   ./app
```

### CI-запуск

```bash
valgrind   --tool=memcheck   --leak-check=full   --show-leak-kinds=all   --errors-for-leak-kinds=definite,indirect,possible   --error-exitcode=42   --log-file=valgrind.%p.log   --suppressions=valgrind.supp   ./tests
```

Если suppression-файла нет, убери параметр `--suppressions=valgrind.supp`.

## 12. Практический алгоритм расследования

Когда увидел сообщение Memcheck:

1. Определи тип ошибки: `Invalid read/write`, `free`, undefined value или leak.
2. Найди первый фрейм своего кода в стеке.
3. Проверь размер операции: `size 1`, `4`, `8` и т. д.
4. Прочитай контекст адреса: после блока, внутри освобождённого блока, до начала блока.
5. Посмотри, где блок был выделен и, если применимо, освобождён.
6. Назови нарушенный инвариант: границы, время жизни, инициализация, владение, парность allocation/deallocation.
7. Исправь причину, а не только симптом.
8. Повтори запуск Valgrind на том же сценарии.
9. После исправления проверь оптимизированную сборку.

## 13. Практика для закрепления

Сделай маленький C++-проект с намеренно внесёнными дефектами:

- выход за границы массива;
- чтение за границей массива;
- use-after-free;
- double free;
- `new[]` + `delete`;
- `malloc` + `delete[]`;
- неинициализированная локальная переменная в `if`;
- неинициализированный буфер в `write`;
- `definitely lost`;
- `indirectly lost`;
- `possibly lost`;
- `still reachable`.

Для каждого случая:

1. Предскажи сообщение Memcheck.
2. Запусти программу под Valgrind.
3. Сверь прогноз с отчётом.
4. Найди место проявления, выделения и освобождения.
5. Исправь код.
6. Добейся чистого отчёта или осознанно документируй `still reachable`/suppression.

## 14. Что изучать дальше

После уверенной практики с Memcheck:

- **Helgrind** и **DRD** — гонки данных, mutex, condition variables, ошибки синхронизации;
- **Massif** — пики потребления heap;
- **DHAT** — частые аллокации и время жизни heap-объектов;
- **Cachegrind** и **Callgrind** — CPU-профилирование, кэш и граф вызовов;
- Valgrind client requests для custom allocators, memory pools и arena allocators.
