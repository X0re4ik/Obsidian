## `std::vector`

### Расскажи, как устроен std::vector под капотом.

`std::vector` хранит элементы в **непрерывном участке памяти**, который выделяется с помощью **аллокатора**. Внутри обычно три указателя: на начало данных, на элемент за последним (`end_`) и на конец выделенной памяти (`end_of_storage_`). Размер объекта на 64-битной системе - 24 байта, но стандарт этого не гарантирует. `size` - число элементов, `capacity` - доступная вместимость. При нехватке места выделяется новый буфер, элементы перемещаются или копируются, а старый освобождается.

### Назови алгоритмическую сложность операций вставки/поиска/удаления для `std::vector`

* `push_back` / `emplace_back` - амортизированно `O(1)`, но `O(N)` при релокации памяти
* `insert` - `O(N)` в начале или середине, в конец - амортизированно `O(1)`
* `std::find` - `O(N)`
* `[]` и `.at()` - `O(1)`
* `clear` - `O(N)`
* `erase` - `O(N)` в начале или середине, последний элемент - `O(1)`

### Есть std::vector из 100 элементов, как работает механика добавления 101 элемента? Добавили 101 элемент, что произойдет при удалении этого элемента?

Есть `std::vector` из 100 элементов.
1. Если `capacity() > 100`, 101-й элемент будет создан в конце: `size()` станет 101, а `capacity()` не изменится.
2. Если `capacity() == 100`, свободного места нет. `vector` выделит новый блок памяти большей ёмкости, переместит или скопирует туда старые элементы, создаст 101-й элемент и освободит старый блок. Точный рост capacity не гарантирован.

При `pop_back()` вызовется деструктор 101-го элемента, `size()` уменьшится до 100, а `capacity()` останется прежней.

### Когда лучше выбирать std::deque, а когда std::vector?

У `std::deque` есть огромное преймущество: добавление в конец и в начало за `O(1)`. Он поддерживает доступность элементов по произвольному доступу за `O(1)`.
Но главное преимущество `std::vector` в его простате, он представляет непрерывный блок памяти, что увеличвает его скорость на больших массивах данных (в т.ч. за счёт попадания кэш-а процессора), возможность управлять размером `capacity` и поддерживать `C API` в виде `.data()`
`std::deque` хорош в довольно узких специализированных задачах по типу реализации скользящего окна и `fifo`


### Что произойдет с итераторами std::vector после вставки/удаления элемента?

Если при вставке не произошла реаллокация, `push_back()` инвалидирует только старый `end()`: итераторы на существующие элементы остаются валидны.
`insert(it, obj)` инвалидирует итератор `it`, все итераторы после него и старый `end()`, потому что элементы с позиции вставки сдвигаются вправо. Корректно сохранить результат так: `it = v.insert(it, obj)`.
`erase(it)` инвалидирует `it`, все итераторы после него и старый `end()`, так как элементы справа сдвигаются влево. Корректная запись: `it = v.erase(it)`.
`pop_back()` инвалидирует итератор на удалённый последний элемент и старый `end()`.
Если любая вставка вызвала реаллокацию, инвалидируются все итераторы, ссылки и указатели на элементы `std::vector`.

### Чем emplace_back отличается от push_back

`emplace_back` конструирует объект непосредственно в памяти вектора, принимая аргументы его конструктора. `push_back` принимает уже созданный объект и копирует или перемещает его. Поэтому при передаче временного объекта `push_back` обычно вызывает перемещение, а `emplace_back` создаёт объект сразу на месте.

```C++
struct User {
  User() { std::cout << "User()\n"; }
  User(const User&) { std::cout << "User(const User&)\n"; }
  User(User&&) noexcept { std::cout << "User(User&&)\n"; }
};

int main() {
  std::vector<User> source;
  source.reserve(10);
  source.push_back(User{});     // User() -> User(User&&)
  source.emplace_back();        // User()
  return 0;
}
```

## std::forward_list

### Расскажи, как устроен std::forward_list под капотом.

`std::forward_list` представляет из себя односторонний список. Односторонний - значит что список поддерживает только операции прохода вперед, то есть `++it`. Сам контейнер хранит только указатель на начало (`head`).

Узлы связанного списка представляют из себя объекты:
```C++
template<typename T>
struct Node {
	T value;    // Данные
	Node* next; // Указатель на следующий элемент в списке
}
```

### Назови алгоритмическую сложность операций вставки/поиска/удаления для std::forward_list.

* Вставка в произвольное место - `O(1)`. Только, если известен итератор на элемент, который находит ДО вставляемого (`insert_after`), иначе - `O(N)`.
* Удаление из произвольного места - `O(1)`. Только, если известен итератор на элемент, который находит ДО удаляемого (`erase_after`), иначе - `O(N)`.
* Поиск элемента - `O(N)`
* Поиск по индексу - невозможен (оператор `operator[]` отсутствует)
* Получить размер элемента - `O(N)` (Нет метода `size`, альтернатива `std::distance(begin(), end())`)

## std::list

### Расскажи, как устроен std::list под капотом.

`std::list` - представляет из себя двухсвязанный список, он поддерживает операции инкремента и декремента для итераторов. Сам контейнер хранит указатель на начало и конец, а также, начиная с `C++11` размер списка (24 байта на `x86-64`)

Узлы связанного списка представляют из себя объекты:
```C++
template<typename T>
struct Node {
	T value;    // Данные
	Node* next; // Указатель на следующий элемент в списке
	Node* prev; // Указатель на предыдущий элемент в списке
}
```

### Чем std::list отличается от std::forward_list? В каких случаях что выбрать?

`std::list` более универсальный список, так как способен итерироваться в обе стороны, операции над контейнером имеют идентичную сложность (исключение для `size`, который для `<C++11` имеет `O(1)` сложность). В подавляющем количестве ситуаций `std::list` приоритетней из-за большей функциональности. Но там, где есть оверхед на память - преимущество за `std::forward_list`.

## std::map

### Расскажи, как устроен std::map под капотом.

`std::map` - это отсоритрованный контейнер, который содержит пары `key/value` значений с уникальностью по ключу. Обычно `std::map` представляет из себя реализацию красно-черного дерева (сбалонсированное двоичное дерево поиска)

**Отметим:**
* У кажого узла дерева может быть не более двух потомков
* Объекты в дереве упорядочены
* Все значения меньше `N` попадают  в левое поддерево, все знаения больше `N` вправое.
* Для каждого узла высоты его правого и левого поддерева примерно равны (в некоторых реализациях они могут отличаться не более чем на 1)

### Назови алгоритмическую сложность операций вставки/поиска/удаления для std::map.

Операции вставки/поиска/удаления дереве будут `O(log(N))`. Теоретически каждая мутабельная операция над деревом может привеси к его перебалансировке, но перебаласировка обычно имеет правила к высоте и "количеству перекрашиваний", так что значимого влияния на скорость операций не даёт. Процесс перебалансировки очень важен, так как не дает дереву "деградировать" в последовательность со скоростью `O(N)`

### Что произойдет с итераторами std::map после перестроения дерева?

Перебалансировка std::map не инвалидирует итераторы, так как элементы хранятся в отдельных узлах дерева и не перемещаются. При erase инвалидируется только итератор на удалённый элемент
### Как использовать свои структуры данных в качестве ключей в std::map?

Так как, `std::map` использует сбалансированное дерево, то для того, чтобы использовать свои структры данных необходимо либо:

1) Опредлить метод `operator<` для структуры
2) Описать свой собственный компаратор

**Пример:**
Вариант 1:
```C++
struct Point {
  int x, y;

  bool operator<(const Point &other) const { return x + y < other.x + other.y; }
};

int main() {
  std::map<Point, int> point_map;
  point_map.insert({Point{1, 2}, 1});
}
```
Вариант 2
```C++
struct Point {
  int x, y;
};

class PointComp {
public:
  bool operator()(const Point &left, const Point &right) const {
    return left.x + left.y < right.x + right.y;
  }
};

int main() {
  std::map<Point, int, PointComp> point_map;
  point_map.insert({Point{1, 2}, 1});
}
```

Требования к сравнению:
1) `a < a` - `false`
2) если `a < b`, то `! (b < 1)`
3) транзитивность
4) если `!(a<b) && !(b<a)`, то `a` эвивалентно `b`

## std::unordered_map

### Расскажи, как устроен std::unordered_map под капотом.

`std::unordered_map` - это хеш-таблица, содержащий пары ключ-значение с уникальными ключами. Поиск, вставка и удаление элементов имеют среднюю постоянную сложность. Внутри элементы не сортируются в каком-либо определённом порядке, а организованы в сегменты. В какой сегмент помещается элемент, полностью зависит от хеша его ключа.

Упрощенно хранение объектов внтури `std::unorderd_map` можно представить так:
```C++
using value_type = std::pair<const Key, T>;
using Bucket = std::list<value_type>;

std::vector<Bucket> buckets_;
```

Типичная реализация выбора бакета выглядит так:
```C++
std::size_t hash = hasher(key);
std::size_t index = hash % bucket_count();
```

### Назови алгоритмическую сложность операций вставки/поиска/удаления для std::unordered_map.

Если ключ имеет "хорошую" хеш-функцию, то операции удаления/вставки/поиска будут `O(1)`, но если "плохую", то каждая операция буде занимать `O(l)`, где `l` - длина цепочки в бакете.

Хорошая хеш-функция - это функция, которая возвращает уникальный индекс объекта, что позволяет иметь короткие цепочки внтури бакета.

В `C++` для стандартных `std` объектов уже реализована специализированная функтор `std::hash` (внтури `<functional>`).

**Пример**
```C++
struct PointHash {
    size_t operator()(const Point& p) const {
        return std::hash<int>()(p.x) ^ (std::hash<int>()(p.y) << 1);
    }
};
```

### Чем std::unordered_map отличается от std::map? Что быстрее?

Два этих контейнера используют разные структуры данных под "капотом", если `std::map` использует сбалансированное красно-черное дерево, то `std::unordered_map` использует хеш-таблицу.
В подавляющем большинстве случаев `std::unordered_map` быстрее `std::map` за счёт доступа к данным, удалением и вставкой, в среднем, за `O(1)`.
Но `std::unordered_map` не поддерживает порядок ключей, сложные ключи будут иметь "дорогую" `hash`-функцию.

### Что такое хеш-функция? Чем отличается хорошая хеш-функция от плохой?

Хеш-функция - это математический алгоритм, который отображает произвольные данные в опредленное фиксированное число. В `C++` хеш-функция имеет следующую сигнатуру (примерно): 
```C++
std::size_t operator()(const Key& key) const;
```

Хорошая хеш-функция:

1) Детерминирована
2) Быстро вычисляется
3) Равномерно распреляет ключи по диапазону `std::size_t`
4) Соблюдает контрак, если `a == b`, то `hash(a) == hash(b)`

### Что такое коллизия? Как разрешается коллизия в std::unordered_map? Какие методы разрешения коллизий ты еще знаешь? Приведи пример коллизии.

Коллизия - ситуация, когда **два разных** ключа имеют **одинаковый хеш-код**.
Основной метод решения колизии - **метод цепочек**. Каждая ячейка содержит указатель на начало списка, коллизия приводит к тому, что в ячейках появляются ссылки на списки размером больше, чем 1 элемент.

**Пример (Плохая хещ-функция)**
```C++
struct BadHash {
  size_t operator()(const std::string &s) const { return s.size(); }
};

int main() {
  std::unordered_map<std::string, int, BadHash> map;

  map["cat"] = 1;
  map["dog"] = 2;

  std::cout << "cat bucket: " << map.bucket("cat") << "\n";
  std::cout << "dog bucket: " << map.bucket("dog") << "\n"; // тот же bucket
}
```

Другие варианты решения колизии: `Open addressing`/`Linear probing`/`Quadratic probing` - хранят элменты прямо в массиве (без указателя на связанный список)

### Что такое рехеш?

Рехеш (`rehash`) - это перестроение хеш-таблицы, при котором изменяется число bucket-ов и все элементы заново распределяются между ними. Его цель - поддерживать небольшой средний размер цепочек внутри bucket-ов и сохранять среднюю сложность поиска, вставки и удаления близкой к `O(1)`.

Упрощенно индекс bucket-ов можно представить так:
```bash
bucket_index = hash(key) % bucket_count;
```

`rehash` обычно происход тогда, когда `max_load_factor() <= size() / bucket_count()`
Его также можно вызвать напрямую через `.rehash(100)` или косвенно через `.reserve(100)`

### Что произойдет с итераторами std::unordered_map после перестроении хеш-таблицы?

Они будут полностью инвалидированы, так как при перестроении хеш-таблцы итератор не сможет ответить на вопрос: Как перейти к следующему элементу именно этого контейнера?

### Как использовать свои структуры данных в качестве ключей в std::unordered_map?

Чтобы использовать свою структуру данных в качестве ключей в `std::unordered_map` необходимо:

1) Хеш-функия для вычисления хеша-а
2) Оператор `operator==` для поиска эквивалентного элемента при колизиях

```C++
struct Point {
  int x, y;

  bool operator==(const Point &other) const {
    return x == other.x && y == other.y;
  }
};

struct PointHash {
  std::size_t operator()(const Point &p) const noexcept {
    std::size_t h1 = std::hash<int>{}(p.x);
    std::size_t h2 = std::hash<int>{}(p.y);
    return h1 ^ (h2 << 1);
  }
};

// Использование:
std::unordered_map<Point, int, PointHash> map;
```

# Умные указатели

## Работа с памятью
### Расскажи про организацию памяти процесса (data, text, BSS и пр.).

`.text`, `.rodata`, `.data`, `.bss` - секции ELF; при запуске они отображаются в память процесса.
- `.text` - машинный код, обычно `R-X`.
- `.rodata` - строковые литералы и данные только для чтения, обычно `R--`.
- `.data` - global/static с ненулевой инициализацией; байты есть в ELF, обычно `RW-`.
- `.bss` - global/static с нулевой инициализацией; место в памяти есть, нулей в ELF нет.
- `stack` - локальные переменные и кадры вызовов; `heap` - `new`/`malloc`.
### Чем отличается `malloc` от `new`?

malloc является низкоурвоневым стредством алокации памяти. ВЫзывая malloc мы запрашиваем блок памяти размером N. Именно поэтому вызов malloc выглядит так:
```C++
int* ptr = (int*)malloc(sizeof(int));
```

`new` это же вернеуровневая конструкция внтри `C++`, которая вызывает алоокацию памяти, а так же вызов конструктора объекта
```C++
struct A {A() {std::cout << "A()" << std::endl }};
auto* a = new A(); // A()
```

### Как `new` понимает, сколько памяти надо выделять?

`new` знает размер, потому что тип указан прямо в выражении: `new T`. Компилятор во время компиляции вычисляет `sizeof(T)` и вызывает соответствующий `operator new`, передавая размер в байтах. После успешного выделения памяти new конструирует объект в этой памяти. Для new `T[n]` вызывается `operator new[]`, а размер может включать дополнительную служебную информацию для последующего `delete[]`.

### Откуда `delete[]` знает, сколько элементов надо удалять?

При `new T[n]` реализация должна знать число элементов, чтобы `delete[]` вызвал их деструкторы в обратном порядке и освободил память. Часто перед массивом хранится `array cookie` с размером. Его формат не стандартизирован, поэтому `new[]` освобождают только через `delete[]`, а `new` - через `delete`.

## std::unique_ptr

### Расскажи про std::unique_ptr. Какими способами его можно создать? Чем эти способы отличаются?

`std::unique_ptr` - умный указатель с единоличным владением и RAII. Его нельзя копировать, но можно перемещать. При уничтожении вызывает deleter: по умолчанию `delete`, а для `unique_ptr<T[]>` - `delete[]`.

Обычно создают через `std::make_unique<T>(args...)`: кратко и безопасно.
Для legacy API или custom deleter: `std::unique_ptr<T, D>{raw, deleter}`.
Для массива: `std::make_unique<T[]>(n)`.

### Зачем нужен std::unique_ptr?

`std::unique_ptr` нужен для безопасного единоличного владения ресурсом по идиоме RAII. Он автоматически освобождает ресурс при выходе из области видимости, поэтому снижает риск утечек, double delete и ошибок при исключениях.

`unique_ptr` нельзя копировать, потому что копия создала бы двух владельцев одного ресурса. Но его можно перемещать, явно передавая владение другому unique_ptr.

По умолчанию он управляет памятью, выделенной через new, и при уничтожении вызывает `delete`. С `custom deleter` он может управлять любым ресурсом, например `FILE*`, сокетом или `handle`. В современном C++ это обычно стандартный выбор, когда владельцев у объекта должен быть ровно один.

### Как устроен std::unique_ptr под капотом?

`std::unique_ptr<T, Deleter>` обычно хранит указатель на ресурс и deleter. При уничтожении, `reset()` или перемещающем присваивании он вызывает `deleter(ptr)`; по умолчанию это `delete`, для `unique_ptr<T[]>` — `delete[]`. Копирование запрещено, перемещение передаёт владение. Пустой deleter обычно не увеличивает размер благодаря EBO, поэтому `unique_ptr<T>` часто равен размеру указателя.

### Какой размер std::unique_ptr?

`std::unique_ptr<T>` со стандартным `std::default_delete<T>` на типичной x64-платформе обычно занимает 8 байт - размер одного указателя.

`unique_ptr` хранит не только указатель на ресурс, но и `deleter`. Если `deleter` пустой, например стандартный `std::default_delete<T>`, реализация обычно применяет `EBO` или `[[no_unique_address]]`, поэтому `deleter` не увеличивает размер объекта. Если указатель свой, то размер увеличивается согласну размеру казателя на платформе.

###  В какой области памяти создается std::unique_ptr?

`std::unique_ptr` - обычный объект, поэтому он размещается там же, где объявлен: локальный `unique_ptr` обычно находится на стеке, поле класса - внутри объекта класса, глобальный - в статической области, а созданный через `new` - в динамической памяти. При этом объект, которым владеет `unique_ptr`, обычно отдельно создаётся через `new` и имеет динамическую длительность хранения.

### Можно ли использовать пользовательский удалитель в std::unique_ptr?

Да, можно. Единсвтенное ограничение, что нельзя использовать создание объекта через `std::make_unqiue<T>(...)`. 
**Пример:**
```C++
std::unique_ptr<PGresult, PGResultDeleter>(new PGresult());
```

### В чём плюсы и минусы использования std::make_unique вместо new при создании std::unique_ptr?

Перечислим недостатки и преимущества `std::unique_ptr` на фоне `std::make_unique`

**Минусы:**
* Отсутствие защиты от утечки памяти при передаче внутрь функции в C++11/14. При передаче аргументов в функцию их порядок не определён. Соответственно, код:
```cpp
f(std::unique_ptr<A>(new A), std::unique_ptr<B>(new B));
```
Может привести к такой последовательности:
1. Создание объекта `A`
2. Создание объекта `B`
3. Исключение до передачи указателя на `A` под владение `std::unique_ptr<A>`
4. Как следствие - утечка памяти
В C++17 этот риск устранён: вычисления аргументов больше не перемежаются.
* Повторение типа при инициализации:
```cpp
std::unique_ptr<A>(new A);
//              ^ повтор типа
```
Плюсы:
* Возможность использования custom deleter

Отметим, что сам код:
```cpp
auto ptr = std::unique_ptr<A>(new A);
```
Полностью безопасен и сам по себе не ведёт к утечке памяти.

## std::shared_ptr
### Расскажи про std::shared_ptr. Какими способами можно его создать? Чем эти способы отличаются?

`std::shared_ptr` это общий указатель, который, в отличии от `std::unique_ptr`, можно копировать. Внутри `std::shared_ptr` есть указатель на данные и, так называемый, контрольный блок - специализированный класс, который подсчитывает количество владельцев объекта.
Создать `std::shared_ptr` можно двумя способами:
1) Напрямую вызовом конструктора: `std::shared_ptr<T>()`
2) При помощи функции `std::make_shared<T>()`
В зависимости от того, какой способ выбрать - создадутся разные контрольные блоки:
* Вызов конструктора - `separate_control_block`
* `std::make_shared<T>()` - `combined_control_block`
Ключевое различие между способами создания. `combined_control_block` создаёт объект внутри себя при помощи механизма `placement new`,  `separate_control_block` только лишь указывает на этот объект, а сам объект находит в другом области памяти. `std::make_shared` является приоритетным способом создания объекта, так как выделение памяти происходит единожды.

## Зачем нужен std::shared_ptr?

`std::shared_ptr` представляет из себя указатель, у которого может быть несколько владельцев.
Например, мы создаем какой-то объект, которым могут владеть несколько других объектов - общий `Config` для нескольких классов обработки. Мы хотим, чтобы при изменении `Config` классы подхватили эти изменения и обрабатывали данные иначе.
**Пример:**
```C++
struct Config { int delay; };

auto c = std::make_shared<Config>(5);

std::vector<Processor> processors = {
	Processor(c),
	Processor(c),
	Processor(c),
	Processor(c)
};
c->delay = 10;
```

## Как устроен std::shared_ptr под капотом? Расскажи про устройство Control Block.

`std::shared_ptr` - "под капотом" содержит указатель на данные и контрольный блок (который так же содержит указатель на данные или хранит у себя данные при помощи механизма `placment new`). Контрольный блок упрощенно можно представить следующим образом:
```C++
struct control_block
{
    virtual void Dispose() = 0;
    virtual void Delete() = 0;
    std::atomic<unsigned long> shareds;
    std::atomic<unsigned long> refs;
};
```

* `shareds` -  количество общих указателей
* `refs` - количество сильный и слабых ссылок
Если `refs == 0`, то вызывается метод `Delete`, который уничтожает контрольный блок, если `shareds == 0`, то вызывается метод `Dispose`, который уничтожает данные, которыми владеет контрольный блок

## Какой размер std::shared_ptr?

`std::shared_ptr` состоит из двух указателей:
* Указатель на контрольный блок
* Указатель на данные
Два указателя на `x86-64` машине весят 16 байт (`8 байт` + `8 байт`)


## В какой области памяти создается std::shared_ptr?

`std::shared_ptr` размещается как обычный объект: локальная переменная обычно на стеке, поле - внутри содержащего объекта, статическая переменная - в статической памяти. Управляемый объект и контрольный блок обычно находятся в динамической памяти. Сам умный указатель весит не много, но дополнительные затраты на память уходят на контрольный блок и поддержку двух указателей на данные.

## Какой тип имеют счетчики ссылок в std::shared_ptr?

Оба счётчика (`shareds` и `refs`) имеют тип `std::atomic<unsigned long>`.
* `unsigned long` потому что значения не могут быть отрицательными
* `std::atomic`, потому что важно, чтобы все операции инкремента и декремента должны быть атомарны и работать в многопоточной среде
Такой подход позволяет управлять **временем жизни** объекта в многопоточной программе **безопасно**, но не гарантирует безопасность при работе с данными.

## В чём плюсы и минусы использования std::make_shared вместо new при создании std::shared_ptr?

**Плюсы:**
* Меньше аллокаций памяти. `std::make_shared` на месте создаст контрольный блок и там же разместит объект  - 1-а аллокация памяти
* Отсутвие утечки памяти при инициализации внутри аргументов функции
```
f(std::make_shared<int>(1), g()) // БЕЗОПАСНО

f(std::shared_ptr<int>(new int{1}), g()) // ВОЗМОЖНА УТЕЧКА ПАМЯТИ, ЕСЛИ g() ВЫБРОСИТ ИСКЛЮЧЕНИЕ (до C++17)
```

**Минусы:**
* Есть одна ситуация, когда `std::make_shared` проигрывает. Она представлена ниже:
```C++
struct Big {
  int data[10000]{};
};

int main() {
  std::weak_ptr<Big> w;
  {
    auto r = std::make_shared<Big>();
    w = r;
  } // (1)

  std::cout << w.use_count() << '\n'; // 0
}
```
Объект `r` создаст в контрольном блоке довольно тяжелый массив, после выхода из блока `(1)` вызовется только деструктор объекта `Big` (такова особенность контрольного блока, созданного при помощи `make_shared`), поэтому память еще будет удержана объектом `w`. 

## std::weak_ptr

## Зачем нужен std::weak_ptr?

`std::weak_ptr` - это умный указатель, который связан с контрольным блоком  `std::shared_ptr`. Он не владеет объектом, но позволяет безопасно сказать существуют ли данные, которыми владеет `std::shared_ptr` (`.lock()` и `.expired()`).

Практическая применимость:
1) Решение проблемы циклических зависимостей:
```C++
struct Node {
    std::shared_ptr<Node> next;
    std::shared_ptr<Node> prev; // цикл
};

struct Node {
    std::shared_ptr<Node> next;
    std::weak_ptr<Node> prev; // не владеет, цикл разорван
};
```
2) Наблюдатель
```C++
std::weak_ptr<Widget> w;

...
w = other_shared_ptr
...

if (auto sp = w.lock()) {
    sp->ulala(); // объект точно жив
}
else { // объект уже удалён
}
```

## Как устроен std::weak_ptr под капотом?

Внутреннее устройство `std::weak_ptr` очень похоже на `std::shared_ptr`, с исключением, что напрямую воспользоваться данными, которые лежат в контрольном блоке через `std::weak_ptr` нельзя, только через вызов `.lock()` (который создаст +1 `std::shared_ptr`) или через `.expired()` (который вернет `true`, если данных уже нет)

Если `std::shared_ptr` удерживает данные и контрольный блок, то `std::weak_ptr` удерживает только контрольный блок и способен продлевать его время жизни.

Весит `std::weak_ptr` столько же, сколько и `std::shared_ptr` - 16 байт на `x86-64`.

## Какой размер std::weak_ptr?

Весит `std::weak_ptr` столько же, сколько и `std::shared_ptr` - 16 байт на `x86-64`.

## Приведи пример того, как ты в своей работе используешь std::weak_ptr.

Кэш ресурсов (например, текстур или соединений), где запись должна «испариться», как только её перестали использовать:
```C++
class ResourceCache {
  std::unordered_map<Key, std::weak_ptr<Resource>> cache_;

public:
  std::shared_ptr<Resource> get(const Key &k) {
    if (auto it = cache_.find(k); it != cache_.end()) {
      // Проверяем, жив ли еще объект
      if (auto sp = it->second.lock())
        return sp;      // Жив, возвращаем
      cache_.erase(it); // Мертв, исключаем ключ
    }
    auto sp = std::make_shared<Resource>(k);
    cache_[k] = sp;
    return sp;
  }
}
```
