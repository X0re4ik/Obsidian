
## 1. Установление соединения — TCP handshake

TCP устанавливает соединение через трёхстороннее рукопожатие:

```text
Клиент                                 Сервер
SYN, SEQ=x ──────────────────────────►
           ◄──────── SYN+ACK, SEQ=y, ACK=x+1
ACK=y+1 ─────────────────────────────►
```

Стороны сообщают начальные номера последовательности и подтверждают их получение. SYN занимает один номер последовательности, поэтому подтверждение равно x+1 или y+1.

Ответ устно: клиент отправляет SYN, сервер отвечает SYN+ACK, клиент подтверждает ответ через ACK. Стороны синхронизируют начальные номера последовательности и устанавливают соединение.

## 2. Контроль скорости передачи данных

Нужно различать два механизма:

| Механизм | От чего защищает | Параметр |
|---|---|---|
| Flow control — управление потоком | Переполнение буфера получателя | rwnd — окно получателя |
| Congestion control — управление перегрузкой | Перегрузка сети | cwnd — окно перегрузки отправителя |

Объём неподтверждённых данных ограничивается меньшим из окон:

```text
Данные в полёте ≤ min(rwnd, cwnd)
```

Это ограничение объёма, а не непосредственно скорости. На скорость также влияет RTT — время прохождения данных и подтверждения.

### Классическая схема TCP Reno

- Slow start: при достаточном потоке ACK окно растёт быстро, примерно удваиваясь за RTT.
- Congestion avoidance: после достижения порога ssthresh рост становится примерно на один MSS за RTT.
- Три повторных ACK: fast retransmit и fast recovery; окно уменьшается, но не сбрасывается до одного MSS.
- Тайм-аут RTO: cwnd уменьшается до одного MSS, начинается slow start.

При входе в fast recovery:

```text
ssthresh = max(FlightSize / 2, 2 MSS)
cwnd = ssthresh + 3 MSS
```

FlightSize — отправленные, но ещё не подтверждённые данные. После подтверждения восстановленных данных cwnd устанавливается в ssthresh. Это классическая схема, а не описание всех современных алгоритмов TCP.

## 3. Окно скольжения

Окно позволяет отправлять несколько сегментов подряд, не ожидая подтверждения каждого. Когда приходят ACK, подтверждённые байты освобождают место для новых — окно «скользит» вперёд. В TCP окно измеряется в байтах.

Упрощённый пример при постоянном размере окна:

```text
Можно иметь 3000 неподтверждённых байтов.
Отправлены:       1–3000
Пришёл ACK=1001:  байты 1–1000 подтверждены
Можно отправить: ещё 1000 байтов, то есть 3001–4000
```

Ответ устно: окно скольжения ограничивает объём неподтверждённых данных и позволяет передавать их непрерывно. По мере поступления подтверждений окно сдвигается, разрешая отправку новых байтов. Передача ограничивается возможностями получателя и состоянием сети.

## 4. Обнаружение и исправление ошибок

TCP использует:

1. Контрольную сумму — для обнаружения повреждений TCP-заголовка и данных. Некорректный сегмент отбрасывается.
2. Номера последовательности и ACK — для отслеживания пропусков, порядка и дубликатов.
3. Повторную передачу — для восстановления потерянных или повреждённых данных. TCP не исправляет отдельные биты, а получает данные заново.

Повторная передача запускается:

- По истечении RTO, если нужное подтверждение не пришло.
- По трём повторным ACK — классический fast retransmit, без ожидания тайм-аута.

### Что означает ACK

```text
Получены байты 1–1000 → ACK=1001
```

ACK указывает следующий ожидаемый байт, а не последний полученный.

```text
ACK=1001  ← исходный
ACK=1001  ← повтор №1
ACK=1001  ← повтор №2
ACK=1001  ← повтор №3 → fast retransmit
```

Нужны три повтора после исходного ACK, а не три ACK суммарно.

### TCP checksum и TTL

Уменьшение TTL на маршрутизаторе меняет контрольную сумму заголовка IPv4, но не TCP checksum: TTL в её расчёт не входит. Контрольная сумма IPv4 покрывает только IP-заголовок. Её можно обновить инкрементально, не пересчитывая весь пакет.

## 5. Закрытие соединения и TIME_WAIT

### Штатное закрытие

Каждое направление закрывается независимо:

```text
A                                      B
FIN ─────────────────────────────────►
    ◄──────────────────────────── ACK
    ◄──────────────────────────── FIN
ACK ─────────────────────────────────►
TIME_WAIT                              CLOSED
```

FIN означает: «Я больше не буду отправлять данные». Другая сторона ещё может передавать свои данные. Обычно происходит обмен FIN → ACK → FIN → ACK, но ACK и FIN могут быть объединены в один сегмент.

Обычные переходы состояний:

```text
Активная сторона:
ESTABLISHED → FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED

Пассивная сторона:
ESTABLISHED → CLOSE_WAIT → LAST_ACK → CLOSED
```

### Зачем нужен TIME_WAIT

В обычном сценарии в него попадает сторона, первой отправившая FIN. Это может быть клиент или сервер.

TIME_WAIT нужен, чтобы:

- Повторно отправить последний ACK, если он потерялся и другая сторона повторила FIN.
- Не допустить смешивания задержавшихся сегментов старого соединения с новым, использующим ту же четвёрку: IP источника, порт источника, IP назначения, порт назначения.

Стандартный интервал — 2 × MSL, где MSL означает максимальное время жизни сегмента. Это не поле TTL. Конкретное время зависит от реализации; в Linux обычно около 60 секунд.

### Почему TIME_WAIT бывает проблемой в проде

При множестве коротких соединений накапливаются записи TIME_WAIT:

- Расходуется память ядра.
- Может не хватить исходящих портов, особенно при частых подключениях к одному IP:port.

Оценка количества записей:

```text
Количество TIME_WAIT ≈ переходы в TIME_WAIT в секунду × время ожидания
```

Например, 1000 переходов в секунду при ожидании 60 секунд дают примерно 60 000 записей. Это не универсальный предел числа соединений.

Основной способ снизить нагрузку — переиспользовать соединения: keep-alive и connection pooling, а не создавать новое соединение на каждый запрос.

### Не путать

- TIME_WAIT — нормальный этап закрытия.
- CLOSE_WAIT — удалённая сторона уже прислала FIN, а локальное приложение ещё не закрыло своё направление. Длительное накопление требует проверки логики приложения.
- tcp_fin_timeout относится к осиротевшим соединениям в FIN_WAIT_2, а не к длительности TIME_WAIT.
- tcp_tw_reuse — механизм безопасного переиспользования при определённых условиях, а не отключение TIME_WAIT; изменять его без диагностики не стоит.

## Общая логика TCP

```text
SYN → SYN+ACK → ACK
Устанавливаем соединение и начальные номера.

SEQ + ACK + скользящее окно
Передаём данные, отслеживаем получение и освобождаем окно.

rwnd + cwnd
Не перегружаем получателя и сеть.

Checksum + повторные передачи
Обнаруживаем повреждения и восстанавливаем данные.

FIN + ACK в обоих направлениях → TIME_WAIT
Завершаем передачу и безопасно закрываем соединение.
```
